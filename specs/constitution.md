# Конституція проєкту

> Незмінні принципи. Кожен `plan.md` містить чекліст відповідності цим статтям.
> Зміна конституції — окрема зміна в `specs/changes/` з ADR у `docs/02` і явним погодженням людини.

Джерела: `docs/03` §1 (стратегія), §9 (Definition of Done); `docs/02` §10 (ADR-01…ADR-10).

---

### Стаття I. Спека перед кодом
Поведінка змінюється лише через специфікацію: `specs/changes/NNN/spec.md` → `plan.md` → `tasks.md`
→ код. Після злиття `specs/capabilities/` знову описує фактичну поведінку. Код, що розходиться зі
спекою, — це баг або у коді, або у спеці; його виправляють, а не ігнорують.

### Стаття II. Детермінованість за замовчуванням (ADR-06)
JSON-LD і декларативні CSS-селектори — основа. LLM — лише каскадний fallback із бюджетом, кешем,
лімітом викликів на прогін і захистом від prompt injection. **Жодного виконання коду,
згенерованого LLM.** Масовий збір не викликає LLM, якщо є детермінована схема.

### Стаття III. Тести офлайн
Жоден тест не звертається до мережі. Сторінки — з `backend/tests/fixtures/`, завантаження — через
`FixtureFetcher`, LLM — через `mock`/фейки. Кожна вимога має тест щасливого шляху, а кожна
відмова/обмеження — тест відмови.

### Стаття IV. Дані продаються разом із походженням (ADR-05, ADR-07)
Кожне поле має `Provenance` (`method`, `confidence`, `source_url`, `observed_at`). Кожен експорт має
маніфест, ліцензію і sha256. Історія `record_versions` — append-only: не переписується, лише
доповнюється (видалення = tombstone-версія).

### Стаття V. Комплаєнс і приватність — архітектура, а не дисклеймер (ADR-09)
- `robots.txt` поважається за замовчуванням; реєстр джерел застосовується примусово
  (`forbidden` — стоп, `high` — підтвердження з причиною в аудит).
- Лише публічні сторінки без авторизації; URL з обліковими даними не запитуються і не зберігаються.
- SSRF-захист для кожного запиту і кожного редиректу.
- PII класифікується на рівні колонки; `personal` **ніколи** не експортується у відкритому вигляді
  і не йде в cloud-LLM.
Послаблення будь-якого з цих правил — лише через зміну конституції.

### Стаття VI. Local-first і захищений локальний API (ADR-02, ADR-08)
Студія працює на одній машині без хмари: SQLite (WAL) — операційний стан, DuckDB — історія (один
writer), файлове сховище — кеш/снапшоти/експорти. API слухає `127.0.0.1`, вимагає Bearer-токен,
відхиляє сторонні `Host`.

### Стаття VII. Усе, що змінює дані, лишає подію
Кожна дія, що змінює задачу, запуск, датасет, політику джерела чи файли, пише подію в журнал
(`events`) з `task_id`, за можливості `run_id`, рівнем і структурованими `data`. Нові типи подій
додаються в каталог `capabilities/00-domain-model.md`.

### Стаття VIII. Типізовані межі та міграції
Межі шарів — Pydantic-моделі (`app/models.py`, `app/api/schemas.py`). Новий стан → forward-only
міграція (SQLite: `MIGRATIONS`; DuckDB: `_migrate`). Старі файли сховища мають відкриватися.

### Стаття IX. Простота і walking skeleton
Один наскрізний робочий шлях цінніший за п'ять напівготових модулів. Важкі рушії/залежності —
optional extras (ADR-03). Нова залежність потребує обґрунтування в `plan.md`.

### Стаття X. Definition of Done (з `docs/03` §9)
1. Спека оновлена; кожна вимога має посилання на тест.
2. Типізовані межі й обробка помилок із причиною (зрозумілою користувачу, українською в UI/API).
3. Подія в журналі для всього, що змінює дані.
4. Міграція схеми, якщо додається стан.
5. Офлайн-тест на щасливий шлях і на відмову.
6. UI-стани (порожній/помилка/завантаження), якщо зміна видима в UI.
7. ADR у `docs/02` для архітектурних рішень; статус у `docs/03`.
8. `ruff`, `pytest` (включно з `test_specs_traceability.py`), `npm run build` зелені.
