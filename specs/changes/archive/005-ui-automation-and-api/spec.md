## 1. Проблема і мета
Бекенд уже підтримує конектор відкритого JSON API (`D-02`), UTC cron-розклад (`P1-05`),
підписки на Telegram/Webhook-доставку дельти (`D-01`) і перевірки якості / gold-set eval
(`P1-01`), але веб-студія не має інтерфейсу для їх налаштування. Оператор змушений користуватися
лише CLI або прямими HTTP-запитами.

**Мета:** зробити весь цикл запуску першого комерційного дата-продукту (від створення задачі
Prozorro/OpenProcurement або кастомного JSON API до розкладу, Telegram/Webhook-підписок і
перевірки якості) керованим з веб-інтерфейсу студії українською мовою.

## 2. Користувацькі сценарії
1. **Як** оператор продукту, **я хочу** у формі створення задачі обрати готовий приклад
   OpenProcurement (Prozorro / Prozorro.Продажі) або задати параметри довільного JSON API, **щоб**
   запустити збір без знання CLI чи JSON-схем бекенду.
2. **Як** оператор, **я хочу** налаштувати cron-розклад задачі та бачити час попереднього й
   наступного запуску прямо у вкладці робочого простору, **щоб** керувати регулярними оновленнями
   візуально і підтверджувати high-risk джерела за потреби.
3. **Як** оператор, **я хочу** додавати, вмикати/вимикати, тестувати й видаляти підписки доставки
   (Telegram і Webhook з фільтрами та HMAC-секретом без показу збереженого секрету у відкритому
   вигляді), **щоб** підключати клієнтів і моніторинг без ручних API-запитів.
4. **Як** оператор, **я хочу** бачити деталі перевірки якості останньої версії та запускати
   офлайн gold-set eval за назвою пресету, **щоб** контролювати точність витягування з UI.

## 3. Вимоги (дельта до `capabilities/13-frontend.md`)

### ADDED

#### REQ-UI-010 — Створення задачі для OpenProcurement та JSON API
Форма створення задачі **ПОВИННА** надавати:
- швидкі приклади для OpenProcurement (`Prozorro API` та `Prozorro.Продажі API`), які заповнюють
  і промпт, і відповідний стартовий публічний API URL;
- опційний згорнутий блок налаштування кастомного `api_source` (шлях до списку, ID, курсор,
  шаблони URL, мапінг полів, інкрементальність), який передається у створення задачі;
- відображення параметрів `api_source` у плані задачі, коли активний режим `api_json`.
- **Сценарій:** GIVEN відкрито діалог «Нова задача» WHEN користувач натискає приклад
  `Prozorro API` THEN підставляються відповідний промпт і seed URL OpenProcurement; при
  заповненому кастомному `api_source` він валідується й передається на бекенд.
- **Відмова:** GIVEN у кастомному `api_source` вказано некоректний JSON мапінгу полів WHEN
  користувач надсилає форму THEN запит не відправляється, а форма показує зрозумілу помилку
  українською.
- **Перевірка:** `npm run typecheck`, `npm run build` (статична перевірка типів і збірки UI;
  автотести UI — прогалина згідно з `13-frontend.md` §4).

#### REQ-UI-011 — Вкладка «Розклад і доставка» (`P1-05` + `D-01`)
Робочий простір задачі **ПОВИНЕН** містити вкладку для керування автоматизацією:
- **Розклад:** відображення поточного cron-розкладу, `next_run_at`, `last_run_at`, швидкі пресети
  інтервалів UTC (`*/15 * * * *`, `0 * * * *`, `0 6 * * *`, `0 6 * * 1`), прапори `enabled` і
  `catch_up`, збереження і видалення, а також обробка HTTP 428 (`high-risk` джерело) через запит
  причини аналогічно `REQ-UI-003`.
- **Доставка дельти:** список підписок (`channel`, `target`, позначка наявності секрету без показу
  самого секрету, активні фільтри), форма створення підписки (`telegram` / `webhook`, фільтри за
  типами змін, ключовими словами, мін./макс. сумою, алерти власнику `notify_on_error`), перемикач
  `enabled`, кнопка «Тест» із показом результату в toast, кнопка видалення.
- Панель **ПОВИННА** мати стани завантаження, порожній стан із підказкою та показ помилок (`REQ-UI-005`),
  весь текст — українською (`REQ-UI-006`).
- **Сценарій:** GIVEN вибрано задачу WHEN користувач відкриває вкладку «Розклад і доставка»,
  обирає пресет розкладу або створює підписку і натискає «Тест» THEN стан оновлюється через API і
  показується toast із результатом.
- **Відмова:** GIVEN бекенд повертає 428 (high-risk) або 400/403 (невалідний cron чи небезпечний
  webhook URL) WHEN користувач зберігає розклад або підписку THEN для 428 запитується причина й
  повторюється запит, а для 400/403 показується toast з текстом `detail`.
- **Перевірка:** `npm run typecheck`, `npm run build`.

#### REQ-UI-012 — Перегляд перевірок якості та запуск gold-set eval у UI (`P1-01`)
У робочому просторі оператор **ПОВИНЕН** бачити детальний розбір `quality_checks` (зауваження
щодо падіння кількості записів чи порожніх обов'язкових полів) і `eval` (F1, Precision, Recall,
LLM fallback %, вартість на 1000 записів), а також мати форму запуску оцінки за назвою
офлайн gold-пресету (`prozorro_gold`, `clinics_gold` тощо) і мінімальним порогом `min_f1`.
- **Сценарій:** GIVEN у задачі є датасет або пресет gold-набору WHEN оператор запускає оцінку
  з вибраним пресетом THEN виконується `eval`, оновлюється робочий простір і відображаються метрики.
- **Відмова:** GIVEN пресет не знайдено або назва некоректна WHEN оператор запускає eval THEN
  API повертає 400 і UI показує toast з помилкою без крашу.
- **Перевірка:** `npm run typecheck`, `npm run build`.

## 4. Нефункціональні вимоги
- Ніяких нових runtime чи build залежностей (використовуємо наявні React 19, TypeScript, Vite).
