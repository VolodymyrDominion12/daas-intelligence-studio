## 1. Проблема і мета
Поточний вбудований профіль OpenProcurement у студії витягує лише дані замовника (назва, ЄДРПОУ, очікувана вартість), але **не** витягує дані компанії-переможця тендера (назва постачальника, ЄДРПОУ переможця, сума й статус присудження). Крім того:
1. Навіть коли збагачення додано вручну до задачі, під час регулярного збору воно не запускається автоматично для нових великих переможців.
2. Пошук сайту компанії та подальший аудит сайту (контакти, соцмережі, технологічний стек) не виконуються за один прохід, якщо пошуковик виконується після аудиту або орієнтується на поле замовника замість переможця.
3. У повідомленнях доставки немає зведеного відображення переможця та його бізнес-контактів.

**Мета:** додати готовий офлайн-профіль **«Prozorro Переможці (B2B Intent)»**, вибір релевантного присудження з масиву JSON API, тригер автоматичного збагачення переможців (пошук сайту → аудит сайту й техстеку) під час збору з порогом суми та відображення результатів у доставці та UI.

**Вимірюваний результат:** за один плановий запуск збору нових великих переможців (наприклад, від 1 млн грн) система детерміновано витягує переможця, автоматично знаходить його офіційний сайт, збирає корпоративні контакти й технології сайту (під повним комплаєнс-захистом) і надсилає готовий B2B-сигнал підписнику без ручного запуску збагачення.

## 2. Користувацькі сценарії
1. **Як** керівник B2B-продажів, **я хочу** створити задачу з промпту про переможців Prozorro або швидкого прикладу в UI, **щоб** одразу отримати колонки переможця (`winner_name`, `winner_edrpou`, `award_amount`, `award_status`), авто-збагачення його сайту/контактів і поріг суми без ручного налаштування JSON-мапінгу.
2. **Як** оператор студії, **я хочу**, щоб після чергового інкрементального збору для кожного нового переможця із сумою вище заданого порогу автоматично запускалися пошук домену та аудит сайту (до ліміту на запуск), **щоб** B2B-підписник миттєво отримував уже збагачений лід.
3. **Як** підписник B2B-тарифу, **я хочу** бачити у Telegram-алерті та XLSX-файлі переможця, ЄДРПОУ, суму присудження, знайдений сайт, бізнес-email, телефон і технології компанії.

### ADDED

#### REQ-PLAN-015 — Офлайн-профіль «Prozorro Переможці (B2B Intent)»
Коли промпт задачі вказує на переможців / постачальників / присудження тендерів Prozorro (або B2B-аудит переможців), планувальник **ПОВИНЕН** формувати спеціалізований `api_json`-план без участі LLM (`limits.max_depth = 0`) із:
- полями закупівлі й переможця (`tender_id`, `title`, `winner_name`, `winner_edrpou`, `award_amount`, `currency`, `award_status`, `award_date`, `name` як замовник, `cpv`, `region`, `status`, `modified_at`, `url`);
- колонками збагачення (`website`, `email`, `phone`, `socials`, `tech_stack`), де контакти мають `pii="business_contact"` (без `pii="personal"`);
- ланцюжком збагачувачів: спершу пошук домену за полем переможця (`winner_name`), потім аудит сайту;
- увімкненим правилом тригера авто-збагачення при зборі (поріг суми: розпізнаний із промпту або `1 000 000` за замовчуванням, статус присудження `active`, обов'язкове поле `winner_name`).
Наявний базовий профіль Prozorro (для звичайних тендерів та аукціонів без запиту на переможців) **ПОВИНЕН** зберігати попередню поведінку.
- **Сценарій:** GIVEN промпт «Знайди переможців тендерів Prozorro через API та проведи аудит їх сайтів» WHEN планування задачі без LLM THEN план має `extraction="api_json"`, поля `winner_name`, `winner_edrpou`, `award_amount`, `award_status`, бізнес-контакти (`pii="business_contact"`), обидва збагачувачі у правильному порядку та активний тригер авто-збагачення з `min_amount=1000000`.
- **Відмова:** GIVEN звичайний промпт «Збери відкриті аукціони Prozorro.Продажі через API» WHEN планування THEN використовується базовий профіль без автоматичного тригера збагачення переможців.
- **Перевірка:** `tests/test_prozorro_winners.py::test_prozorro_winners_preset_and_trigger_config`

#### REQ-EXT-011 — Фільтрований вибір елемента масиву в JSON API (`key[field=value]`)
Декларативний екстрактор JSON API **ПОВИНЕН** підтримувати фільтрований вибір першого відповідного об'єкта зі списку у форматі `шлях[поле=значення]` (регістронезалежне порівняння рядкового значення поля), сумісний із резервними гілками через `|`.
- **Сценарій:** GIVEN JSON тендера, де перше присудження має статус `unsuccessful`, а друге — `active` WHEN мапінг використовує `awards[status=active].suppliers.0.name|awards.0.suppliers.0.name` THEN витягується назва переможця з другого (активного) присудження.
- **Відмова:** GIVEN JSON, де жодне присудження не відповідає фільтру, і немає резервної гілки WHEN екстракція THEN поле безпечно лишається порожнім без винятку.
- **Перевірка:** `tests/test_prozorro_winners.py::test_json_path_filtered_award_selection`

#### REQ-ENR-012 — Послідовний waterfall для переможця та тригер авто-збагачення при зборі
Система **ПОВИННА** забезпечувати:
1. Коли збагачувач пошуку сайту має налаштоване цільове поле імені (наприклад, `winner_name`) або воно присутнє в записі, пошук виконується саме за назвою компанії-переможця (та її регіоном/містом), не підміняючи її назвою замовника, і не запускається, якщо переможець відсутній;
2. Якщо в одному прогоні збагачення (`enrich` або авто-тригер) для одного запису активні пошук сайту й аудит сайту, пошук сайту **ПОВИНЕН** виконуватися перед аудитом сайту, щоб знайдений у цьому ж проході `website` одразу проходив аудит (`site_audit` + `tech_detect`) без другого ручного запуску;
3. Коли в специфікації задачі увімкнено тригер авто-збагачення, після завершення етапу збору (до формування снапшоту, diff і доставки змін) система **ПОВИННА** відібрати записи з поточного збору, що задовольняють умовам тригера (наявні обов'язкові поля, відповідний статус, сума `>= min_amount`, і ще не мають заповнених полів збагачення), виконати їх збагачення в межах ліміту `max_records_per_run` через той самий комплаєнс-фільтр (`robots.txt`, SSRF, реєстр джерел), дописати append-only ревізію в історію й записати подію `auto_enrichment_triggered`. Помилка чи блокування комплаєнсу на окремому сайті компанії **НЕ ПОВИННА** зривати фіксацію зібраних тендерів чи доставку решти змін.
- **Сценарій:** GIVEN задача з активним тригером авто-збагачення (`min_amount=1000000`) і два нові тендери: один з активним переможцем на 1 250 000 грн без `website`, другий на 85 000 грн WHEN завершується збір THEN авто-збагачення спрацьовує лише для першого: знаходить сайт переможця, знімає email/телефон/техстек, дописує ревізію у версію збору, фіксує подію `auto_enrichment_triggered`, і ці поля потрапляють у снапшот та доставку.
- **Відмова:** GIVEN запис із сумою менше порогу, або без переможця, або вже збагачений, або домен переможця заборонено реєстром джерел WHEN завершується збір THEN перші три пропускаються без зовнішніх запитів, а заборонений домен блокується комплаєнсом із подією `compliance_blocked` без збою збору.
- **Перевірка:** `tests/test_prozorro_winners.py::test_collect_winner_trigger_resolves_domain_and_audits_site`, `tests/test_prozorro_winners.py::test_winner_trigger_respects_threshold_idempotency_and_compliance`

#### REQ-DEL-007 — B2B-контекст переможця та збагачених контактів у доставці
Під час формування повідомлень доставки (`telegram` та `webhook` / `xlsx`) система **ПОВИННА**:
- брати суму запису для фільтрів (`min_amount` / `max_amount`) і форматування з `award_amount` (якщо вона є) або `amount`/`price`;
- включати у Telegram-повідомлення назву переможця, ЄДРПОУ (за наявності), знайдений сайт, бізнес-email, телефон і перші позиції техстеку, при цьому безумовно маскуючи будь-які колонки `pii="personal"` і не маскуючи `pii="business_contact"`.
- **Сценарій:** GIVEN збагачений запис переможця (`winner_name`, `winner_edrpou`, `award_amount=1250000`, `website`, `email` з `pii="business_contact"`, `tech_stack`) і `telegram`-підписка з `min_amount=1000000` WHEN доставляється дельта THEN фільтр пропускає запис за `award_amount`, а повідомлення містить дані переможця й бізнес-контакти без `[redacted]`.
- **Відмова:** GIVEN у тій самій задачі поле з `pii="personal"` WHEN доставка THEN особисте поле замінюється на `[redacted]` до формування тексту і фільтрації.
- **Перевірка:** `tests/test_prozorro_winners.py::test_winner_delivery_formats_contacts_and_protects_personal_pii`

#### REQ-UI-018 — Швидкий приклад «Prozorro Переможці (B2B)» і керування тригером у UI

## 4. Нефункціональні вимоги
- **Без нових залежностей:** жодних додаткових бібліотек не потрібно.
- **Офлайн-тести:** пошук домену (`SearchProvider`) і завантаження сайтів переможців тестуються через локальні фейки/фікстури (`FixtureFetcher`), без реальної мережі.
- **Комплаєнс і безпека:** усі запити авто-збагачення проходять через `PolicyGuardFetcher` із перевіркою реєстру джерел, `robots.txt` та SSRF; `pii="personal"` лишається під безумовним захистом, тоді як корпоративні реквізити переможця позначаються як `pii="business_contact"`.
- **Контроль вартості та часу збору:** `max_records_per_run` (1–200, за замовчуванням 20) гарантує обмежену кількість зовнішніх аудитів на один запуск.

## 6. Відкриті питання
- Закрито за `docs/06` і існуючою архітектурою:
  - Авто-збагачення налаштовується опційним об'єктом на `TaskSpec` (`default=None`), щоб старі задачі в SQLite відкривалися без міграції БД.
