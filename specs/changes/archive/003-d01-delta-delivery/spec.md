## 1. Проблема і мета
Зараз виявлені зміни (`new_entity`, `price_drop`, `field_changed`, `removed_entity`) лишаються
тільки всередині журналу подій студії й UI. Для комерційного алерт-сервісу по відкритих тендерах
і аукціонах (`Prozorro` / `Prozorro.Продажі`) релевантна дельта після завершення збору має
автоматично доставлятися підписникам у **Telegram** і на **Webhook**, без дублів після рестарту,
без витоку персональних PII і з миттєвим службовим сповіщенням власнику про збої або 0 записів.

**Мета:** додати підписки на доставку дельти на рівні задачі (канали Webhook і Telegram),
детерміновану фільтрацію (тип зміни, ключові слова, діапазон суми), ідемпотентну дедуплікацію,
повторні спроби при тимчасових збоях та службові алерти власнику.

**Вимірюваний результат:** після завершення прогону відфільтровані зміни доставляються у
підключений канал (або безпечно пропускаються при збігу ключа дедуплікації), поля `personal`
PII завжди маскуються, а помилки доставки чи збору не ламають основний прогін і фіксуються в журналі.

## 2. Користувацькі сценарії
1. **Як** підписник алерт-бота, **я хочу** налаштувати підписку з фільтром за ключовими словами,
   мінімальною сумою та типом події (`new_entity`, `price_drop`), **щоб** отримувати у Telegram лише
   релевантні лоти без спаму.
2. **Як** B2B-клієнт, **я хочу** підключити Webhook із HMAC-підписом для передачі дельти в n8n / CRM,
   **щоб** автоматизувати реакцію менеджерів на нові закупівлі й падіння цін.
3. **Як** власник сервісу, **я хочу** отримувати службовий алерт у разі падіння прогону (`run_failed`)
   або 0 зібраних записів, **щоб** оперативно реагувати на зміни в API або збої парсингу.

## 3. Вимоги (дельта до `capabilities/`)

### ADDED

#### REQ-DEL-001 — Керування підписками на доставку дельти (API і CLI)
Система **ПОВИННА** дозволяти створювати, переглядати, оновлювати, тестувати й видаляти підписки на
доставку для конкретної задачі (канали `webhook` або `telegram`, фільтри `event_types`, `keywords`,
`min_amount`, `max_amount`, `notify_on_error`, прапор `enabled`, опційний секрет підпису webhook).
Небезпечні webhook URL (локальні/приватні адреси без дозволу або URL із обліковими даними)
**ПОВИННІ** відхилятися (HTTP 400). Секрет підпису **НЕ ПОВИНЕН** повертатися відкритим текстом у
відповідях API чи подіях. Створення, оновлення і видалення підписки пишуть події
`subscription_created`, `subscription_updated`, `subscription_deleted`.
- **Сценарій:** GIVEN існуюча задача WHEN користувач створює `webhook`- або `telegram`-підписку
  з фільтрами THEN підписка зберігається, API повертає маскований статус секрету, пишеться подія
  `subscription_created`.
- **Відмова:** GIVEN `webhook` із адресою `http://127.0.0.1:9000/hook` при вимкненому доступі до
  приватної мережі WHEN створення підписки THEN HTTP 400 (SSRF-захист), підписка не зберігається.
- **Перевірка:** `tests/test_delivery.py::test_subscription_crud_ssrf_and_secret_masking`,
  `tests/test_delivery.py::test_cli_notify_commands`

#### REQ-DEL-002 — Детермінована фільтрація, маскування PII та форматування повідомлень
Перед відправленням дельти система **ПОВИННА**:
- відбирати лише зміни увімкнених підписок, що відповідають усім заданим фільтрам (`event_types`,
  регістронезалежні `keywords` у записі, `min_amount` / `max_amount`);
- безумовно приховувати/маскувати значення колонок із `pii="personal"` перед виходом у будь-який
  зовнішній канал (`[redacted]`);
- для `webhook` формувати JSON-пакет дельти (і заголовок `X-Daas-Signature: sha256=...` за наявності
  секрету), для `telegram` — безпечно екрановане HTML-повідомлення через Telegram Bot API.
- **Сценарій:** GIVEN дві підписки (одна з фільтром `price_drop` і ключовим словом `"меблі"`, друга
  з порогом `min_amount=100000`) WHEN після збору знайдено лот на 150 000 з `"меблі"` і полем
  `pii="personal"` THEN релевантні підписки отримують відфільтровані сповіщення з прихованим PII.
- **Відмова:** GIVEN зміна, що не підпадає під жоден фільтр підписки WHEN завершення збору THEN
  зовнішній запит не виконується.
- **Перевірка:** `tests/test_delivery.py::test_delta_filtering_pii_redaction_and_hmac`

#### REQ-DEL-003 — Ідемпотентна дедуплікація, повторні спроби, SSRF на редиректі та алерти власнику
Система **ПОВИННА**:
- гарантувати, що кожна подія зміни версії або службовий алерт доставляються по конкретній підписці
  **щонайбільше один раз** (персистентний журнал дедуплікації переживає перезапуск);
- виконувати повторні спроби (до налаштованого ліміту) при мережевих помилках / HTTP `429` / `5xx`,
  не повторювати `4xx` (крім `429`) і блокувати небезпечні URL перед кожним запитом без автоматичного
  слідування редиректам;
- при `notify_on_error=true` надсилати службовий алерт власнику, якщо запуск завершився з `failed` або
  дав 0 записів;
- фіксувати результат подіями `delivery_sent` або `delivery_failed` (`warning`, без токенів/секретів
  у тексті), не зриваючи фіксацію самого збору даних.
- **Сценарій:** GIVEN тимчасовий `503` на першій спробі і `200` на другій WHEN доставка дельти
  THEN запит повторюється, доставка завершується успіхом (`delivery_sent`), а повторний виклик
  диспетчера для тих самих змін більше не надсилає дубль.
- **Відмова:** GIVEN збій Telegram/Webhook після вичерпання спроб або `failed`-прогін із
  `notify_on_error=true` WHEN доставка THEN пишеться `delivery_failed` (без токена бота в журналі)
  або службовий алерт власнику, а дані зібраної версії лишаються збереженими.
- **Перевірка:** `tests/test_delivery.py::test_delivery_retries_dedup_and_owner_error_alerts`

## 4. Нефункціональні вимоги
- **Без нових важких залежностей:** доставка працює поверх наявного `httpx` і стандартного
  `hmac`/`hashlib`.
- **Офлайн-тести:** усі тести використовують `httpx.MockTransport` або фейковий транспорт, без
  звернень до реального Telegram чи зовнішніх URL.
- **Приватність та безпека:** SSRF-перевірка кожного webhook, заборона облікових даних в URL,
  маскування `pii="personal"`, приховування `DAAS_TELEGRAM_BOT_TOKEN` і `secret` у логах/API.
- **Сумісність сховища:** forward-only міграція SQLite №6; старі БД (`user_version <= 5`)
  відкриваються автоматично.

## 5. Поза скоупом
- Google Sheets / Email SMTP-канали (можна додати наступними каналами поверх тієї самої таблиці

  на Тижні 4.
- UI-форма редагування підписок у React (у `003` оновлюємо контракти `api.ts`/`types.ts`).

## 6. Відкриті питання
- Вирішено на основі `docs/05` §5 (Тиждень 2):
