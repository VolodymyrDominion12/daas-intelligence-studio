## 1. Проблема і мета
Зараз збір даних запускається лише вручну (кнопкою в UI, через API або CLI). Для алерт-сервісу
по відкритих тендерах і аукціонах (`Prozorro` / `Prozorro.Продажі`) дані мають оновлюватися
автоматично за розкладом кожні N хвилин або годин — усередині процесу студії, без конфліктів
блокування DuckDB, із захистом від накладання прогонів та безпечним доганянням після простою.

**Мета:** додати вбудований cron-планувальник на задачу зі збереженням розкладів у локальному
сховищі, API/CLI-керуванням, дотриманням комплаєнсу й захистом від паралельних дублів.

**Вимірюваний результат:** задача з налаштованим cron-розкладом автоматично запускає `collect`
у визначений час, пропускає тик при активному запуску, виконує рівно один доганяючий прогін
після перезапуску/пропуску і пише прозорі події в журнал.

## 2. Користувацькі сценарії
1. **Як** власник алерт-сервісу, **я хочу** задати cron-розклад на задачу збору (наприклад,
   `*/15 * * * *`), **щоб** студія автоматично забирала нові лоти й зміни ціни без ручного
   втручання.
2. **Як** оператор студії, **я хочу**, щоб у разі затягнутого попереднього прогону новий запуск за
   розкладом безпечно пропускався, **щоб** не створювалися конфлікти і помилки блокування.
3. **Як** адміністратор VPS, **я хочу**, щоб після короткого рестарту або простою студії
   прострочений розклад виконав **один** доганяючий прогін (а не десятки накопичених прогонів
   підряд), **щоб** дані швидко актуалізувалися без перевантаження джерела.

## 3. Вимоги (дельта до `capabilities/`)

### ADDED

#### REQ-RUN-040 — Конфігурація та валідація cron-розкладу на задачу
Система **ПОВИННА** дозволяти створювати, оновлювати, переглядати та видаляти cron-розклад
для конкретної задачі (стандартний 5-польовий cron `хвилина година день місяць день_тижня` або
макроси `@hourly`, `@daily`, `@weekly`, прапори `enabled` і `catch_up`, опційне підтвердження
`high`-ризику з причиною ≥ 10 символів). Некоректний cron-вираз або відсутність причини при
підтвердженні високого ризику **ПОВИННІ** відхилятися з помилкою валідації (HTTP 422 / 400).
Зміна чи видалення розкладу **ПОВИННІ** фіксуватися подією в журналі (`schedule_updated` /
`schedule_deleted`).
- **Сценарій:** GIVEN існуюча задача WHEN користувач задає валідний розклад `*/15 * * * *`
  THEN розклад зберігається з обчисленим часом наступного запуску (`next_run_at`) і пишеться подія
  `schedule_updated`.
- **Відмова:** GIVEN невалідний cron-вираз (наприклад `"99 * * * *"`) WHEN збереження розкладу
  THEN HTTP 422 і розклад не зберігається.
- **Перевірка:** `tests/test_scheduler.py::test_cron_validation_and_schedule_crud_api`

#### REQ-RUN-041 — Автоматичний запуск за розкладом і захист від накладання
Планувальник **ПОВИНЕН** періодично перевіряти увімкнені розклади, для яких настав час запуску
(`next_run_at <= now`), і запускати збір (`collect`):
- якщо в задачі вже є активний запуск — пропустити слот, пересунути `next_run_at` у майбутнє і
  записати подію `schedule_skipped`;
- якщо спрацьовує комплаєнс-заборона (`forbidden` / `needs_ack`) або відсутнє обов'язкове
  калібрування для веб-задачі — **не** запускати збір, записати подію `schedule_blocked`
  (`level="warning"`) і пересунути `next_run_at` у майбутнє;
- інакше — запустити `collect`, оновити `last_run_at` / `last_run_id`, пересунути `next_run_at`
  у майбутнє та записати подію `schedule_triggered`.
- **Сценарій:** GIVEN увімкнений розклад із `next_run_at <= now` і вільна задача WHEN тік
  планувальника THEN стартує новий `collect`-запуск, оновлюється `next_run_at > now`, у журналі
  з'являється `schedule_triggered`.
- **Відмова:** GIVEN активний запуск задачі або домен, переведений у `forbidden` WHEN тік
  планувальника THEN новий запуск не створюється, `next_run_at` переноситься вперед, у журналі
  записується `schedule_skipped` або `schedule_blocked`.
- **Перевірка:** `tests/test_scheduler.py::test_scheduler_triggers_skips_active_and_respects_compliance`

#### REQ-RUN-042 — Доганяючий прогін після простою (`catch_up`)
Якщо розклад був пропущений на кілька інтервалів (наприклад, через перезапуск процесу), система
**ПОВИННА**:
- при `catch_up=true` — виконати **рівно один** доганяючий запуск (а не цикл по всіх
  пропущених слотах) і встановити наступний слот строго після поточного часу (`> now`);
- при `catch_up=false` і запізненні більше ніж на 120 секунд — пропустити прострочений слот із
  подією `schedule_skipped` і пересунути `next_run_at` на наступний слот `> now`.
- **Сценарій:** GIVEN `next_run_at` відстає від `now` на 3 години і `catch_up=true` WHEN тік
  планувальника THEN виконується 1 запуск і `next_run_at` стає строго більшим за `now`.
- **Відмова:** GIVEN `next_run_at` відстає від `now` на 3 години і `catch_up=false` WHEN тік
  планувальника THEN запуск пропускається з подією `schedule_skipped` (`reason="missed_no_catchup"`),
  новий запуск не створюється.
- **Перевірка:** `tests/test_scheduler.py::test_scheduler_catch_up_and_missed_slot_policy`

## 4. Нефункціональні вимоги
- **Один writer DuckDB:** планувальник виконується всередині процесу студії (`daas serve`), тому
  не виникає конфлікту блокування файлу DuckDB.
- **Без нових важких залежностей:** парсинг стандартного 5-польового `cron` реалізується легким
  детермінованим модулем без зовнішніх важких бібліотек.
- **Офлайн-тести:** усі тести планувальника використовують інжектований час (`now`) і офлайн
  `FixtureFetcher` без очікування реальних хвилин чи звернень у мережу.
- **Сумісність сховища:** існуючі SQLite-файли відкриваються автоматично (forward-only міграція
  №5).

## 5. Поза скоупом
- Довільні таймзони IANA на рівні кожного розкладу (у v1 усі `cron`-вирази обчислюються в UTC —
  послідовно зі зберіганням усіх дат у ISO-UTC в БД).
- Окремий розподілений воркер / Celery / Redis (`P2-04`).
- UI-форма для редагування розкладу в React (у зміні `002` оновлюємо `api.ts`/`types.ts` для
  сумісності API-контракту, а екранний UI винесемо після завершення `D-01`).

## 6. Відкриті питання
- Вирішено на основі `docs/03` §3.3 та `docs/05` §2:
  - Час `cron` у `002` працює в UTC (узгоджено з `utcnow()` у всій базі коду).
  - Налаштування: `DAAS_SCHEDULER_ENABLED` (за замовчуванням `true`) та `DAAS_SCHEDULER_POLL_SECONDS`
    (за замовчуванням `15.0`).
  - Підтримується стандартний 5-польовий синтаксис (`*`, числа, діапазони `a-b`, кроки `*/n` та
    `a-b/n`, списки `a,b,c`) плюс макроси `@hourly`, `@daily`, `@weekly`.
