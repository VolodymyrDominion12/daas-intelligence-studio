## 1. Проблема і мета
Зараз дедуплікація у студії лише показує список схожих пар без можливості прийняти рішення: злити дві сутності в один канонічний запис або відхилити хибний збіг. Крім того, повторні інкрементальні збори не знають про вже злиті дублікати.

Мета: реалізувати персистентне керування зв'язками сутностей (`merged` / `dismissed` / `unmerged`), детерміновану політику вирішення конфліктів полів, повністю оборотне роз'єднання без втрати append-only історії версій, урахування канонічних зв'язків при інкрементальному зборі, а також інтерактивну UI-чергу перевірки дублікатів і CLI-команди.

## 2. Користувацькі сценарії
1. **Як** аналітик даних, **я хочу** переглянути пару кандидатів на дублікат із порівнянням полів та вибрати правило злиття (довіра / свіжість / повнота / пріоритет A або B), **щоб** об'єднати дублікати в один якісний канонічний запис без втрати заповнених даних.
2. **Як** оператор студії, **я хочу** роз'єднати раніше злиті записи в один клік, **щоб** повернути обидва вихідні записи у датасет зі збереженням повної історії змін.
3. **Як** оператор студії, **я хочу** позначити пару як «Не дублікат», **щоб** вона більше не засмічувала чергу перевірки при наступних переглядах.
4. **Як** власник регулярного моніторингу, **я хочу**, щоб повторний збір по вже злитому дублікату автоматично оновлював канонічний запис замість повторної появи дубліката.

## 3. Вимоги (дельта до `capabilities/`)

### ADDED

#### REQ-ENR-010 — Детермінована політика злиття, інкрементальне порівняння та канонічний редірект
Система **ПОВИННА**:
- надавати детерміноване злиття двох записів за політикою (`confidence` | `freshness` | `completeness` | `prefer_left` | `prefer_right`) та опційним ручним перевизначенням окремих полів: порожні значення одного запису заповнюються з іншого, масиви об'єднуються без дублікатів, конфлікти скалярних полів вирішуються політикою, а змінені/конфліктні поля отримують походження `method="merge"` із посиланням на вихідне джерело без послаблення PII-маркування;
- підтримувати інкрементальне виявлення дублікатів (порівняння нових записів лише з наявними канонічними кандидатами через blocking по домену, телефону та префіксу назви);
- під час інкрементального збору скеровувати оновлення раніше злитого ключа запису на його активний канонічний ключ, не відроджуючи поглинутий дублікат окремим рядком.
- **Сценарій:** GIVEN два записи одного об'єкта з різною свіжістю, довірою й повнотою полів WHEN виконується злиття за обраною політикою THEN канонічний запис містить усі заповнені поля, переможця конфлікту за політикою та `provenance.method == "merge"` для злитих полів; WHEN при наступному зборі приходить оновлення поглинутого ключа THEN воно оновлює канонічний запис.
- **Відмова:** GIVEN невідома політика злиття WHEN викликається злиття THEN система відхиляє запит з помилкою валідації.
- **Перевірка:** `tests/test_entity_merge.py::test_deterministic_merge_policies_and_incremental_dedupe`,
  `tests/test_entity_merge.py::test_incremental_collect_redirects_merged_key_to_canonical`

#### REQ-ENR-011 — Персистентні зв'язки сутностей, оборотне злиття та роз'єднання без втрати історії
Система **ПОВИННА**:
- зберігати рішення щодо пар сутностей (канонічний ключ, поглинутий/парний ключ, статус `merged` | `dismissed` | `unmerged`, схожість `score`, правило `rule`, політика, автор і ревізії до злиття) з forward-only міграцією старого операційного сховища;
- під час злиття додавати нову append-only ревізію канонічного запису, маркувати поглинутий запис новою tombstone-ревізією (`deleted=true`), оновлювати лічильник рядків датасету та записувати подію `entity_merged`;
- дозволяти відхилити пару кандидатів (`dismissed`) з виключенням із черги кандидатів та подією `duplicate_dismissed`;
- під час роз'єднання (`unmerge`) активного злитого зв'язку відновлювати обидва записи до стану до злиття новими append-only ревізіями (`deleted=false`) **без видалення жодної історичної ревізії**, оновлювати лічильник рядків, переводити зв'язок у статус `unmerged` та записувати подію `entity_unmerged`.
- **Сценарій:** GIVEN два активні записи у датасеті WHEN виконується злиття, а згодом роз'єднання THEN після злиття кількість активних рядків зменшується на 1 і видно об'єднаний payload; після роз'єднання обидва записи знову активні з початковими полями, а повна історія ревізій (включно зі злиттям і tombstone) збережена.
- **Відмова:** GIVEN відсутній ключ або неіснуючий зв'язок WHEN викликається merge або unmerge THEN повертається `KeyError`/404; GIVEN спроба злити запис сам із собою або повторно злити вже поглинутий запис чи роз'єднати неактивний зв'язок THEN повертається помилка `400`/`409`.
- **Перевірка:** `tests/test_entity_merge.py::test_old_sqlite_migrates_to_entity_links`,
  `tests/test_entity_merge.py::test_merge_dismiss_and_reversible_unmerge_api`,
  `tests/test_entity_merge.py::test_out_of_order_unmerge_replays_later_merges`

#### REQ-API-010 — HTTP API та CLI для merge, dismiss і unmerge дублікатів
Система **ПОВИННА** надавати захищені Bearer-токеном ендпоінти та CLI-команди:
- `GET /api/tasks/{id}/duplicates?threshold=88` — повертає кандидатів (із виключенням активних `merged` і `dismissed` пар, прев'ю полів та оцінкою ідентичності), `scanned`, `note` та список `links`;
- `POST /api/tasks/{id}/duplicates/merge` — злиття двох записів за обраною політикою (`200`, `400` для однакових/некоректних параметрів, `404` для відсутньої задачі/запису, `409` при конфлікті з уже злитим записом);
- `POST /api/tasks/{id}/duplicates/dismiss` — відхилення пари (`200`, `400`/`404`/`409`);
- `POST /api/tasks/{id}/duplicates/links/{link_id}/unmerge` — роз'єднання активного зв'язку (`200`, `404`/`409`);
- CLI команди `daas merge <task_id> <canonical_key> <merged_key> [--policy ...]` та `daas unmerge <task_id> <link_id>`.
- **Сценарій:** GIVEN задача зі схожими записами WHEN клієнт API або CLI отримує чергу, зливає пару, перевіряє `links`, а потім роз'єднує зв'язок THEN відповіді відповідають контракту і синхронно оновлюють датасет.
- **Відмова:** GIVEN виклик без токена (коли auth увімкнено) або з невідомим `task_id` / `link_id` / конфліктом стану THEN API відповідає `401` / `404` / `409` українською, CLI завершується з ненульовим кодом.
- **Перевірка:** `tests/test_entity_merge.py::test_merge_dismiss_and_reversible_unmerge_api`,
  `tests/test_entity_merge.py::test_cli_merge_and_unmerge`

#### REQ-UI-014 — Інтерактивна черга дублікатів із merge/dismiss/unmerge у веб-інтерфейсі
Веб-інтерфейс (`DuplicatesPanel` і `TaskWorkspace`) **ПОВИНЕН** бути синхронним із API-контрактом (`types.ts`, `api.ts`) і надавати:
- вибір порогу схожості та політики злиття (довіра / свіжість / повнота / пріоритет A або B);
- для кожного кандидата — порівняння полів записів A і B, показ якості ідентичності, кнопки «Злити в A», «Злити в B» і «Не дублікат»;
- перелік активних та історичних зв'язків сутностей із кнопкою «Роз'єднати» для активних злитих записів та автоматичним оновленням лічильника рядків і таблиці даних;
- стани завантаження, порожньої черги та відображення помилок.
- **Сценарій:** GIVEN вкладка «Дублікати» у веб-інтерфейсі WHEN користувач зливає пару або роз'єднує активний зв'язок THEN черга та лічильник рядків оновлюються без перезавантаження сторінки.
- **Відмова:** GIVEN серверна помилка (409/404) при дії користувача THEN UI показує toast із причиною помилки і повертає елемент у доступний стан.
- **Перевірка:** `npm run typecheck`, `npm run build` (прогалина JS-рендер тестів за `13-frontend.md` §4)

## 4. Нефункціональні вимоги
- Усі тести повністю офлайн (`FixtureFetcher`, тимчасові SQLite/DuckDB), без звернень до мережі чи LLM.
- Append-only інваріант `record_versions` зберігається суворо: ані `merge`, ані `unmerge` не видаляють історичних рядків.
- PII-поля (`pii="personal"`) не експортуються відкрито і не потрапляють у публічні події; запити до DuckDB строго параметризовані.
- Старі файли `operational.sqlite` без таблиці зв'язків мігрують forward-only автоматично при старті.
