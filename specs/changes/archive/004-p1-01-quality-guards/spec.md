## 1. Проблема і мета
Зараз студія рахує лише відсоток заповненості колонок (`fill_rates`), але не сигналізує про
аномальне падіння обсягу після змін у джерелі, порожні обов'язкові поля та не вимірює реальну
точність витягування (precision / recall / F1) на еталонних зразках (gold-set). Без цього не можна
гарантувати якість алертів та вибірок для клієнтів і вчасно ловити регресії парсерів у CI.

**Мета:** після кожного збору/збагачення автоматично перевіряти базові інваріанти якості датасету з
алертом власнику при порушенні, а також надати повністю офлайновий gold-set eval через CLI та API
зі збереженням метрик у маніфест версії датасету.

## 2. Користувацькі сценарії
1. **Як** власник продукту, **я хочу** автоматично отримувати попередження (подію і алерт), якщо
   новий прогін зібрав удвічі менше записів за попередню версію або залишив порожніми обов'язкові
   поля, **щоб** помітити злам API/верстки раніше за клієнтів.
2. **Як** розробник або оператор, **я хочу** запускати `daas eval --task <id> --gold <path>` або
   `POST /api/tasks/{id}/eval` на локальних фікстурах, **щоб** бачити precision/recall/F1, coverage,
   % LLM-fallback та зупиняти регресію в CI, якщо F1 падає нижче порогу.

## 3. Вимоги (дельта до `capabilities/`)

### ADDED

#### REQ-QUAL-001 — Автоматичні перевірки якості після прогону
Система **ПОВИННА** після завершення збору або збагачення (під час фіксації версії датасету)
виконувати детерміновану перевірку якості та записувати звіт у `manifest.quality_checks` версії:
- **Аномальне падіння кількості записів:** якщо попередня версія мала `rows > 0`, а частка втрати
  `(prev_rows - row_count) / prev_rows > DAAS_QUALITY_MAX_DROP_RATIO` (за замовчуванням `0.5`),
  фіксується проблема `row_count_drop`;
- **Порожні обов'язкові колонки:** якщо `row_count > 0` і заповненість будь-якої обов'язкової не-AI
  колонки (`required=true`) нижча за `DAAS_QUALITY_MIN_REQUIRED_FILL_PCT` (за замовчуванням `80.0`),
  фіксується проблема `required_field_empty`.

Якщо перевірка виявила проблеми (`passed=false`):
- **Сценарій:** GIVEN завершений прогін `collect`/`enrich` з аномалією (падіння >50% або порожнє обов'язкове поле) WHEN фіксується версія датасету THEN у `manifest.quality_checks` записано `passed=false` і перелік проблем, у журналі з'являється подія `quality_warning` (`warning`), і підписники з `notify_on_error=true` отримують алерт `quality_warning`.
- **Відмова:** GIVEN збій при доставці алерту `quality_warning` WHEN завершується прогін THEN версія датасету, записи та снапшот усе одно зберігаються успішно (попередження не відкочує валідний збір).
- **Перевірка:** `tests/test_quality.py::test_post_run_quality_guards_pass_and_warn`, `tests/test_quality.py::test_quality_warning_sends_owner_alert`

#### REQ-QUAL-002 — Офлайн gold-set eval та поріг регресії
Система **ПОВИННА** надавати повністю офлайновий eval-харнес для задачі на локальному gold-set наборі
(HTML або JSON API кейси з очікуваними записами без мережевих запитів):
- обчислювати `precision`, `recall`, `f1`, `coverage` по оцінюваних полях та агреговано,
  `llm_fallback_pct` і `usd_per_1k_records`;
- перевіряти поріг регресії `f1 >= min_f1` (за замовчуванням `DAAS_EVAL_MIN_F1 = 0.8`);
- зберігати результат у `manifest.eval` останньої версії датасету (якщо версія існує) та писати
  подію `eval_completed` (`info` при `passed=true`, `warning` при `passed=false`, без витоку сирих
  PII-значень);
- надавати `POST /api/tasks/{id}/eval` (inline-кейси або безпечне ім'я вбудованого gold-пресету) і
  CLI `daas eval --task <id> --gold <path> [--min-f1 <float>]` (код виходу `1`, якщо `passed=false`).
- **Сценарій:** GIVEN задача (Prozorro API JSON або HTML каталог) і відповідний офлайн gold-set WHEN запускається eval через CLI або API THEN метрики `f1 >= min_f1`, `passed=true`, результат збережено в `dataset_versions.manifest.eval` і зафіксовано подією `eval_completed`.
- **Відмова:** GIVEN деградований екстрактор (хибний селектор/мапінг) або небезпечне ім'я пресету з path traversal (`../`) чи неіснуюча задача WHEN викликається eval THEN F1 падає нижче порогу (`passed=false`, CLI виходить з кодом `1`), небезпечний шлях/порожній набір відхиляється з HTTP 400, невідома задача — з HTTP 404.
- **Перевірка:** `tests/test_quality.py::test_gold_eval_api_json_and_html_regression_gate`, `tests/test_quality.py::test_eval_endpoint_and_cli_exit_codes`

## 4. Нефункціональні вимоги
- Повністю офлайн: `run_gold_eval` і тести не виконують жодних мережевих запитів.
- Безпека: API `POST /api/tasks/{id}/eval` не приймає довільних шляхів файлової системи (тільки
  валідовані inline-кейси або безпечний ідентифікатор пресету `[a-zA-Z0-9_-]+`); PII-значення
  записів не пишуться в журнал подій `eval_completed`.
- Продуктивність: детермінована оцінка на 20–50 фікстурах виконується за < 1 с.
