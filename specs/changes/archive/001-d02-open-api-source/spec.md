## 1. Проблема і мета
Зараз студія вміє завантажувати та розбирати лише HTML/XML-сторінки і потребує попереднього
CSS-калібрування. Це блокує підключення стабільних відкритих REST JSON API (зокрема Prozorro та
Prozorro.Продажі), які є найкращою точкою старту для першого комерційного дата-продукту без
антибот-боротьби, проксі й витрат на LLM.

**Мета:** навчити студію збирати, пагінувати та інкрементально оновлювати записи з публічного
JSON API за декларативним описом полів — із тими самими гарантіями комплаєнсу, історії змін,
tombstones та офлайн-тестів, що й для веб-сторінок.

**Вимірюваний результат:** задача з відкритим API тендерів/аукціонів збирає записи з офлайн
JSON-фікстур без викликів LLM і без CSS-калібрування, фіксує нові сутності та зміни ціни/статусу
між прогонами й зберігає стабільний ідентифікатор запису.

## 2. Користувацькі сценарії
1. **Як** розробник дата-продукту, **я хочу** створити задачу для відкритого JSON API
   (Prozorro / Prozorro.Продажі або іншого REST-ендпоінту) з декларативним мапінгом полів,
   **щоб** збирати структуровані дані без крихких CSS-селекторів і без витрат на LLM.
2. **Як** власник сервісу сповіщень, **я хочу**, щоб повторний збір по API читав лише сторінки,
   змінені після попереднього курсора/часової мітки (з опційним повним проходом), **щоб** не
   перевантажувати джерело і швидко ловити нові лоти або зниження ціни (`price_drop`).
3. **Як** відповідальний за безпеку й комплаєнс, **я хочу**, щоб API-запити проходили ті самі
   перевірки `robots.txt`, реєстру джерел, logged-out, SSRF і rate-limit, що й HTML-сторінки,
   **щоб** не з'явилися «бічні двері» для обходу політик.

### ADDED

#### REQ-DM-009 — Конфігурація режиму збору з відкритого JSON API
Схема задачі **ПОВИННА** підтримувати декларативний режим джерела «відкритий JSON API» з явним
мапінгом шляхів JSON на колонки задачі, способом пагінації (курсор або зміщення), шляхом до
масиву елементів, ключем унікального ідентифікатора сутності та опційним посиланням на детальний
ресурс. Якщо в конфігурації джерела вказано приватну мережу або облікові дані в URL —
валідація задачі **ПОВИННА** відхилятися так само, як для HTML seed-ів.
- **Сценарій:** GIVEN валідний запит створення задачі з типом джерела JSON API та мапінгом
  колонок WHEN задача зберігається THEN конфігурація джерела зберігається без втрати полів і
  доступна для збору.
- **Відмова:** GIVEN конфігурація API-джерела з порожнім мапінгом полів або URL з токеном доступу
  WHEN створення/оновлення задачі THEN помилка валідації (HTTP 422 / 403) і задача не створюється.
- **Перевірка:** `tests/test_open_api_source.py::test_api_source_spec_validation_and_logged_out`

#### REQ-PLAN-012 — Шаблон задачі для відкритого API закупівель і аукціонів
Планувальник **ПОВИНЕН** розпізнавати запит на збір із відкритого API тендерів/аукціонів (таких як
Prozorro та Prozorro.Продажі) і формувати готовий набір колонок та налаштування JSON-мапінгу без
участі LLM (ключові поля: ідентифікатор, назва/предмет, замовник, категорія/CPV, регіон,
очікувана вартість/стартова ціна, валюта, статус, дата зміни/дедлайн, публічне посилання).
Персональні дані (`pii="personal"`) у базовій схемі **НЕ ПОВИННІ** використовуватися.
- **Сценарій:** GIVEN LLM вимкнено WHEN користувач створює задачу для Prozorro / Prozorro.Продажі
  THEN план містить валідну схему колонок без `pii="personal"` і декларативний API-мапінг.
- **Відмова:** GIVEN промпт із вимогою авторизованого приватного кабінету чи збору персональних
  контактів за логіном WHEN планування задачі THEN задача відхиляється або не включає приватний
  URL (відповідно до правил logged-out).
- **Перевірка:** `tests/test_open_api_source.py::test_openprocurement_preset_builds_non_pii_api_spec`

#### REQ-FETCH-011 — Підтримка JSON-відповідей під тим самим комплаєнс-захистом
Завантажувач **ПОВИНЕН** дозволяти отримання відповідей із JSON `Content-Type` (`application/json`,
`application/*+json`) у режимі API-джерела, зберігаючи без винятків перевірки SSRF, редиректів,
реєстру джерел, logged-out, `robots.txt`, rate-limit, обмеження розміру відповіді (до 6 МБ) та
збереження в raw-кеш.
- **Сценарій:** GIVEN публічний JSON API-ендпоінт і дозвільна політика в реєстрі WHEN виконується
  запит у режимі API THEN відповідь успішно повертається і кешується з коректним `final_url`.
- **Відмова:** GIVEN JSON-ендпоінт із `tos_risk=forbidden` або редирект на приватну IP-адресу
  WHEN запит у режимі API THEN запит блокується (`policy` або `unsafe`) без мережевого виклику
  до забороненої цілі.
- **Перевірка:** `tests/test_open_api_source.py::test_fetcher_json_mode_and_compliance_guard`

#### REQ-EXT-010 — Декларативна екстракція з JSON-відповіді
Для JSON-документа система **ПОВИННА** детерміновано витягувати один або кілька записів за
вказаним шляхом до списку та декларативними шляхами полів (включно з вкладеними об'єктами),
приводити значення до типів колонок, виставляти стабільний ключ запису на основі офіційного
ідентифікатора з API (якщо вказано в конфігурації) і позначати походження кожного поля
методом `api_json` без виклику LLM.
- **Сценарій:** GIVEN JSON-відповідь зі списком із 3 тендерів/лотів WHEN екстракція THEN
  повертаються 3 `ExtractedRecord` зі стабільними ключами `api:<id>` та валідним `Provenance`.
- **Відмова:** GIVEN невалідний (битий) JSON або порожній список елементів WHEN екстракція THEN
  повертається 0 записів без падіння прогону, а помилка розбору фіксується в журналі подій.
- **Перевірка:** `tests/test_open_api_source.py::test_json_extractor_maps_fields_and_handles_broken_json`

#### REQ-RUN-029 — Інкрементальна пагінація та деталізація API-записів
Під час збору з JSON API система **ПОВИННА**:
- переходити по наступних сторінках/курсорах (`next_page` або `offset`) у межах `limits.max_pages`;
- підтримувати збереження останнього успішного курсора/мітки часу між запусками (інкрементальний
  режим), щоб наступний прогін завантажував лише оновлення, а також режим повного проходу;
- якщо конфігурація задає детальний URL за ідентифікатором елемента — довантажувати картки
  елементів через ту саму стійку чергу з дотриманням rate-limit і перевіркою комплаєнсу.
- **Сценарій:** GIVEN API повертає 2 сторінки списку за курсором WHEN запуск збору THEN оброблено
  обидві сторінки, курсор збережено після успішної фіксації версії, і повторний запуск починає
  з останнього збереженого курсора.
- **Відмова:** GIVEN тимчасова 429/5xx помилка на другій сторінці або перерваний запуск WHEN
  пагінація THEN прогін позначає помилку згідно таксономії retry, а інкрементальний курсор
  **НЕ ПОВИНЕН** зсуватися вперед поверх необроблених сторінок.
- **Перевірка:** `tests/test_open_api_source.py::test_api_collection_pagination_cursor_and_failure_safety`,
  `tests/test_open_api_source.py::test_sqlite_migration_v4_opens_v3_database`

#### REQ-RUN-030 — Запуск збору API-задачі без CSS-калібрування
Для задачі з налаштованим декларативним режимом JSON API запуск збору **ПОВИНЕН** дозволятися
одразу без попереднього CSS-калібрування (не повертати HTTP 409 про відсутність калібрування).
- **Сценарій:** GIVEN задача у статусі `draft` з конфігурацією JSON API WHEN користувач запускає
  збір THEN збір стартує без `skip_calibration=true`, зберігає версію датасету і рахує дельту змін.
- **Відмова:** GIVEN звичайна HTML-задача без конфігурації JSON API і без калібрування WHEN запуск
  збору без `skip_calibration=true` THEN поведінка не змінюється (HTTP 409).
- **Перевірка:** `tests/test_open_api_source.py::test_api_collection_pagination_cursor_and_failure_safety`

### MODIFIED

#### REQ-FETCH-006 — Дозвіл JSON поруч із HTML/XML для режиму API
Було: відповідь відхиляється як `permanent`, якщо `Content-Type` не містить `html`/`xml`.
Стане: за замовчуванням для веб-сторінок дозволено лише `html`/`xml`, а при явному дозволі
формату `json` (режим JSON API) дозволяється також `application/json` та `application/*+json`;
інші типи контенту (бінарні файли, зображення, архіви) як і раніше відхиляються як `permanent`.
- **Перевірка:** `tests/test_open_api_source.py::test_fetcher_json_mode_and_compliance_guard`

#### REQ-CAL-008 — Уточнення вимоги калібрування для декларативного JSON API
Було: `POST /run` без збереженого калібрування повертає 409, якщо не передано `skip_calibration=true`.
Стане: те саме правило діє для HTML-задач; для задач із валідною декларативною схемою JSON API
калібрування є опційним і `POST /run` дозволяється одразу.
- **Перевірка:** `tests/test_open_api_source.py::test_api_collection_pagination_cursor_and_failure_safety`

## 4. Нефункціональні вимоги
- **Офлайн-тести:** усі тести нового адаптера й пагінації використовують локальні JSON-фікстури в
  `backend/tests/fixtures/` і `FixtureFetcher` або `httpx.MockTransport` без мережевих викликів.
- **Комплаєнс і PII:** жодного збору за логіном; поля обмежуються публічними атрибутами тендерів/
  аукціонів та юридичних осіб; `policy`-блокування застосовується до кожного URL пагінації та
  деталей.
- **Детермінованість і LLM-витрати:** 0 LLM-викликів на плануванні шаблону та масовому зборі API.
- **Сумісність сховища:** існуючі SQLite/DuckDB файли без API-конфігурації повинні відкриватися
  без помилок і без втрати старих даних (forward-only міграція за потреби).
- **Навантаження на джерело:** дотримання `DAAS_PER_DOMAIN_RPS` і `Retry-After`.
