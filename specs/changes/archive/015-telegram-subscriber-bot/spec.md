## 1. Проблема і мета
Зараз створення та налаштування підписок доставки (`telegram`) виконується лише вручну оператором через веб-інтерфейс студії або `daas notify` CLI. Коли кількість кінцевих підписників (тарифів Free / Pro / B2B Intent) зростає:
1. Ручний онбординг кожного користувача (введення `chat_id`, CPV, регіонів, бюджету, стоп-слів, паузи) створює операційне навантаження на власника.
2. Немає механізму самообслуговування користувачем власної підписки (перемикання режиму `instant`/`digest`, пауза, ручний запуск дайджесту, перегляд статусу й оплати).
3. Потрібна ізоляція між процесом аналітики (один writer DuckDB) та взаємодією з Telegram Bot API.

**Мета:** реалізувати окремий тонкий Telegram-бот підписника, який спілкується зі студією **виключно через її захищений REST API** (без прямого доступу до DuckDB чи SQLite), надає 7-денний ознайомчий період (`Free Trial`), покрокове або командне налаштування фільтрів, керування паузою/дайджестом і посилання на оплату (`/upgrade`).

**Вимірюваний результат:** новий підписник за `< 60 секунд` у діалозі з ботом обирає потік моніторингу, налаштовує CPV/регіон/бюджет/стоп-слова/режим, отримує реальну підписку у студії й може керувати нею (`/status`, `/pause`, `/resume`, `/flush`, `/upgrade`) без участі оператора.

## 2. Користувацькі сценарії
1. **Як** новий B2B-користувач, **я хочу** надіслати боту `/start`, обрати потік закупівель/переможців та задати свої CPV-префікси, регіон, мінімальний бюджет і стоп-слова, **щоб** одразу почати отримувати релевантні алерти в межах 7-денного Free Trial.
2. **Як** підписник, **я хочу** переглянути статус тарифу (`/status`), тимчасово призупинити сповіщення (`/pause`), відновити їх (`/resume`) або достроково забрати накопичений дайджест (`/flush`), **щоб** контролювати потік повідомлень самостійно.
3. **Як** власник студії, **я хочу**, щоб користувачі без активного платного плану чи тріалу обмежувалися режимом щоденного дайджесту й отримували `/upgrade`-посилання на оплату, а успішна оплата активувала тариф `pro`/`b2b` через захищений платіжний webhook або CLI.

### ADDED

#### REQ-DEL-008 — Тонкий Telegram-бот підписника поверх REST API студії
Окремий сервіс Telegram-бота **ПОВИНЕН**:
- взаємодіяти зі студією виключно через її HTTP REST API (`/api/tasks`, `/api/tasks/{id}/subscriptions*`) із `Authorization: Bearer` (без імпорту чи прямого доступу до DuckDB та операційної SQLite-бази студії);
- суворо ізолювати підписників: кожен Telegram `chat_id` бачить і змінює **лише** власні підписки (`channel="telegram"` і `target == str(chat_id)`), ніколи не отримуючи дані інших користувачів, Webhook URL чи секрети/токени студії;
- підтримувати як текстові команди (`/...`), так і натискання inline callback-кнопок Telegram.
- **Сценарій:** GIVEN у студії є задача моніторингу та підписки двох різних `chat_id` (плюс Webhook-підписка) WHEN `chat_id=101` викликає `/status` або `/pause` THEN бот повертає та змінює лише підписки з `target="101"`, не торкаючись `chat_id=202` і Webhook-підписки.
- **Відмова:** GIVEN недоступний API студії або відсутній/невалідний Bearer-токен WHEN користувач надсилає команду THEN бот повертає коректне повідомлення українською про тимчасову недоступність сервісу без витоку токенів чи stacktrace.
- **Перевірка:** `tests/test_subscriber_bot.py::test_bot_uses_studio_rest_api_and_isolates_chat_ids`

#### REQ-DEL-009 — 7-денний Free Trial, тарифні обмеження (`free`/`trial`/`pro`/`b2b`) та `/upgrade`
Сервіс бота **ПОВИНЕН** підтримувати персистентний стан профілів підписників (`free`, `trial`, `pro`, `b2b` із датою завершення дії):
- при першому `/start` нового `chat_id` автоматично активується ознайомчий `trial` на `DAAS_BOT_TRIAL_DAYS` днів (за замовчуванням `7`);
- користувач із активним `trial`, `pro` або `b2b` має повний доступ до вибору режиму доставки (`instant` і `digest_daily`);
- користувач на плані `free` або із протермінованим `trial`/`pro`/`b2b` обмежується режимом `digest_daily`: спроба увімкнути `instant` відхиляється з підказкою `/upgrade`;
- команда `/upgrade` **ПОВИННА** показувати доступні тарифи та (якщо налаштовано `DAAS_BOT_PAYMENT_URL`) безпечне HTTPS/HTTP посилання на оплату з підстановкою `chat_id`.
- **Сценарій:** GIVEN новий користувач надіслав `/start` WHEN він викликає `/status` і вмикає `/mode instant` THEN активний 7-денний тріал дозволяє зберегти `delivery_mode="instant"`.
- **Відмова:** GIVEN користувач із протермінованим тріалом (`free`) WHEN він намагається увімкнути `/mode instant` THEN підписка не переводиться в `instant`, а бот відповідає повідомленням про обмеження безкоштовного плану та пропозицією `/upgrade`.
- **Перевірка:** `tests/test_subscriber_bot.py::test_bot_free_trial_upgrade_and_plan_enforcement`

#### REQ-DEL-010 — Самообслуговування фільтрів, пауза, відновлення та ручний дайджест у боті
Бот **ПОВИНЕН** надавати повний цикл самообслуговування підписки поверх REST API студії:
- вибір цільової задачі моніторингу (`/select <id|номер>` або вибір кнопкою після `/start`);
- налаштування фільтрів: CPV-префікси (`/cpv ...|all`), регіони (`/region ...|all`), мінімальний/максимальний бюджет (`/budget <min[-max]>|0`), позитивні ключові слова (`/keywords ...|clear`), стоп-слова (`/exclude ...|clear`), режим доставки (`/mode instant|digest`) — кожна зміна створює або оновлює Telegram-підписку користувача в студії;
- призупинення (`/pause`) та відновлення (`/resume`) активних підписок користувача;
- ручна відправка накопиченого дайджесту (`/flush`);
- зрозумілі повідомлення про помилку українською при некоректних аргументах (напр., нечисловий бюджет, неіснуюча задача, відсутність обраної задачі).
- **Сценарій:** GIVEN користувач обрав задачу Prozorro WHEN він задає `/cpv 4531`, `/region Київ`, `/budget 1000000`, `/exclude канцтовари`, `/mode instant` і далі `/pause` та `/resume` THEN у студії створюється й оновлюється відповідна `telegram`-підписка з точними полями `DeliveryFilters`, а `/pause`/`/resume` перемикають її `enabled`.
- **Відмова:** GIVEN нечисловий бюджет (`/budget abc`) або вибір неіснуючої задачі (`/select unknown`) WHEN команда обробляється THEN бот повертає підказку формату без HTTP-винятку та без пошкодження наявної підписки.
- **Перевірка:** `tests/test_subscriber_bot.py::test_bot_filter_setup_pause_resume_and_flush`

#### REQ-DEL-011 — Webhook/Polling режим бота, захищений платіжний webhook, конфігурація та CLI
Система **ПОВИННА** надавати:
- HTTP-додаток бота з ендпоінтами: `GET /health`, `POST /telegram/webhook` (перевіряє заголовок `X-Telegram-Bot-Api-Secret-Token`, якщо задано `DAAS_BOT_WEBHOOK_SECRET`; невірний або відсутній токен → `401`) та `POST /billing/webhook` (активує тариф `pro`/`b2b` на вказану кількість днів лише після перевірки `DAAS_BOT_BILLING_SECRET` через `X-Billing-Secret` або HMAC `X-Signature`; якщо секрет не налаштовано → `503`, невірний підпис → `401`);
- long-polling цикл бота (`getUpdates`) для локального запуску без публічного домену;
- CLI-команди `daas bot serve [--mode polling|webhook --host --port]`, `daas bot status [--chat-id ...]`, `daas bot grant <chat_id> --plan <free|trial|pro|b2b> [--days 30]`;
- типізовані налаштування `DAAS_BOT_*` у `Settings` та `.env.example` із коментарями.
- **Сценарій:** GIVEN налаштовано `DAAS_BOT_WEBHOOK_SECRET` та `DAAS_BOT_BILLING_SECRET` WHEN приходить валідний webhook оплати (`pro`, `30` днів) і далі валідний Telegram webhook з `/status` THEN план підписника оновлюється на `pro` та відображається в `/status`.
- **Відмова:** GIVEN запит до `/telegram/webhook` чи `/billing/webhook` з відсутнім або підробленим секретом WHEN обробляється запит THEN повертається HTTP `401` (або `503` при вимкненому billing-секреті) без зміни стану.
- **Перевірка:** `tests/test_subscriber_bot.py::test_bot_webhooks_polling_and_cli_commands`

## 4. Нефункціональні вимоги
- **Без нових runtime-залежностей:** реалізація працює на наявних `httpx`, `FastAPI`, `Pydantic v2`, `Typer` (без важких зовнішніх бот-фреймворків).
- **Збереження ADR-02 (один writer DuckDB):** бот працює виключно через HTTP REST API студії та власний легкий JSON-файл стану підписників (атомарний запис), ніколи не відкриваючи DuckDB-файл студії.
- **Офлайн-тести:** усі тести взаємодіють з локальним `TestClient` студії через `httpx.MockTransport` та замоканим Telegram Bot API без реальної мережі.
- **Приватність та безпека:** бот не логує і не повертає користувачам `DAAS_TELEGRAM_BOT_TOKEN`, `DAAS_API_TOKEN`, `DAAS_BOT_WEBHOOK_SECRET`, `DAAS_BOT_BILLING_SECRET` або чужі `chat_id`.

## 5. Поза скоупом
- Повноцінна інтеграція з конкретною платіжною системою (Monobank/Paddle API-клієнт) понад універсальний `/upgrade` URL і захищений `POST /billing/webhook`.
- Мульти-адмінський веб-кабінет управління підписниками в React UI (окремий беклог P3-02).
- Публічні pSEO-сторінки (`019`) та Google Sheets доставка (`017`).

## 6. Відкриті питання
- Закрито за `docs/06` та архітектурою студії:
  - Стан профілів підписників бота (`free`/`trial`/`pro`/`b2b`) і тимчасового вибору задачі зберігається в окремому файлі `DAAS_BOT_STATE_FILE` (у `storage/`), щоб сервіс бота був повністю відокремленим від БД студії й працював поверх її REST API.
  - Безкоштовний план після завершення `trial` зберігає створені підписки, але обмежує режим до `digest_daily` при спробі перемкнутися на `instant` через бота.
