## 1. Проблема і мета
У `DuckDB` вже є таблиця `quarantine`, але пайплайн туди нічого не спрямовує: підозрілі або частково пошкоджені записи (наприклад, елементи з невалідним типом поля після приведення, відсутнім ідентифікуючим полем, менш ніж 2 валідними полями чи критично низькою впевненістю) або мовчки відкидаються, або забруднюють датасет. Крім того, оператор не має ані API, ані вкладки в студії, щоб побачити причину потрапляння в карантин та підтвердити або відхилити такий запис.

Мета: автоматично й детерміновано відправляти підозрілі записи в карантин із зрозумілою українською причиною, дати API та UI («Карантин») для перегляду, підтвердження (перенесення в датасет) або видалення записів.

## 2. Користувацькі сценарії
1. **Як** оператор студії, **я хочу** бачити підозрілі або частково некоректні витягнуті записи у вкладці «Карантин» із точною причиною відбраковування, **щоб** виявляти зміни верстки/API без засмічення основного датасету.
2. **Як** оператор студії, **я хочу** підтвердити придатний запис із карантину (перенести в основний датасет) або відхилити сміттєвий, **щоб** підтримувати чистоту даних і мати аудит таких рішень.

## 3. Вимоги (дельта до `capabilities/`)

### ADDED

#### REQ-HIST-040 — Автоматичне спрямування підозрілих записів у карантин та міграція схеми
Під час збору (`HTML` або `api_json`) система **ПОВИННА** детерміновано перевіряти кандидати записів і замість мовчазного відкидання або запису аномалії спрямовувати їх у карантин з унікальним `id`, `source_url`, `payload`, `created_at` і зрозумілою причиною, якщо:
1. кандидат має ≥ 1 витягнутого поля, але після очищення/приведення типів лишається `< 2` валідних полів (за наявності `>= 2` джерельних колонок у задачі) або відсутнє ідентифікуюче поле (`name/title/company/website/phone/email/address` для HTML);
2. не-порожнє значення мапленого поля в `api_json` не вдалося привести до оголошеного `dtype` колонки;
3. середня впевненість (`mean_confidence`) запису нижча за `0.40`.

Записи, у яких просто відсутнє опційне або even `required=true` значення (без помилки приведення типу й за наявності `>= 2` валідних полів), **НЕ ПОВИННІ** карантинитися на рівні рядка (їх контролюють пост-ран інваріанти `REQ-QUAL-001`). Кожен карантинений елемент збільшує `stats.records_quarantined` і пише подію `record_quarantined` (`warning`). Старі бази DuckDB без колонки `id` у таблиці `quarantine` **ПОВИННІ** мігрувати forward-only без втрати даних.
- **Сценарій:** GIVEN сторінка HTML з елементом, де `rating="не число"` лишає лише 1 валідне поле, або API-відповідь з `amount="invalid"` WHEN виконується збір THEN елемент записується в `quarantine` із причиною, `stats.records_quarantined >= 1`, а основний `current_records` не забруднюється.
- **Відмова:** GIVEN валідні дані (вкл. запис без `amount`, де `value` відсутній у JSON) WHEN виконується збір THEN `quarantine` лишається порожнім і пост-ран перевірки `REQ-QUAL-001` працюють без регресії.
- **Перевірка:** `tests/test_quarantine.py::test_old_duckdb_quarantine_is_migrated`,
  `tests/test_quarantine.py::test_runner_quarantines_suspect_html_and_api_records`

#### REQ-HIST-041 — HTTP API карантину: перегляд, підтвердження та відхилення
Система **ПОВИННА** надавати захищені Bearer-токеном ендпоінти:
- `GET /api/tasks/{id}/quarantine?limit&offset` — пагінований список карантинних записів (`id`, `run_id`, `source_url`, `reason`, `payload`, `created_at`, `total`);
- `POST /api/tasks/{id}/quarantine/{item_id}/approve` — перенесення запису в append-only `record_versions` (із `Provenance(method="manual", verified=True, ...)` та оновленням `row_count` датасету), видалення з карантину та запис події `quarantine_approved`;
- `DELETE /api/tasks/{id}/quarantine/{item_id}` — остаточне відхилення запису з карантину та запис події `quarantine_dismissed`.
- **Сценарій:** GIVEN у задачі є запис у карантині WHEN клієнт викликає `GET /quarantine`, потім `POST /quarantine/{item_id}/approve` THEN запис з'являється у `GET /records`, кількість у датасеті зростає, з карантину запис зникає, і в журналі з'являється `quarantine_approved`.
- **Відмова:** GIVEN неіснуючий `task_id` або `item_id` WHEN клієнт викликає `GET`/`POST approve`/`DELETE` THEN API повертає `404` з українським повідомленням; при `DELETE` існуючого елемента повертається `200 {deleted: true}` без додавання запису в датасет.
- **Перевірка:** `tests/test_quarantine.py::test_quarantine_api_list_approve_dismiss_and_404`

#### REQ-UI-013 — Вкладка «Карантин» у веб-інтерфейсі
`TaskWorkspace` і `QuarantinePanel` **ПОВИННІ** показувати вкладку «Карантин» (з лічильником за наявності елементів > 0), перелік відхилених записів із датою, джерелом, причиною і JSON-переглядом полів, кнопки «Підтвердити в датасет» та «Відхилити», а також стани завантаження, порожнього списку та обробку помилок.
- **Сценарій:** GIVEN задача має записи в карантині WHEN користувач відкриває вкладку «Карантин» і натискає підтвердити/відхилити THEN список оновлюється і відображає актуальний стан без перезавантаження сторінки.
- **Відмова:** GIVEN порожній карантин або помилка API WHEN відкривається вкладка THEN відображається підказка порожнього стану або повідомлення про помилку (toast/banner).
- **Перевірка:** `npm run typecheck`, `npm run build` (прогалина JS-рендер тестів за 13-frontend §4)

#### REQ-EXT-006 — Виправлення підрахунку валідних полів після приведення типів
Було: `_is_usable` рахував мінімум `>= 2` полів до видалення невалідних за `dtype` значень.

## 4. Нефункціональні вимоги
- Повна сумісність офлайн-тестів (жодних мережевих викликів).
- SQL у DuckDB виконується виключно через параметризовані запити.
- PII не витікає у тексти подій (`record_quarantined`, `quarantine_approved`, `quarantine_dismissed` містять `item_id`/`record_key`/`reason`, без сирих персональних контактів).
- Усі тексти причин, API `detail`, подій та UI — українською мовою.

## 5. Поза скоупом

- Зберігання відхилених/видалених карантинних записів після явного `DELETE`.
