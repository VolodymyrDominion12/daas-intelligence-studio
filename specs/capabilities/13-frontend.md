## 1. Призначення
Одна сторінка-студія українською: список задач, створення задачі, робочий простір із вкладками,
живий журнал подій. UI — тонкий клієнт над API (11); бізнес-правила живуть у backend.

## 2. Структура

| Компонент | Відповідальність |
|:---|:---|
| `App` | конфіг, список задач, вибрана задача, polling кожні 2.6 с, SSE-журнал, toast-и |
| `Sidebar` | список задач, статуси, кнопка «Нова задача» |

## 3. Вимоги

### REQ-UI-001 — Токен і API-клієнт
Клієнт **ПОВИНЕН** брати токен з `<meta name="daas-token">` (вбудовується backend-ом) або з
`__DAAS_TOKEN__` (Vite dev читає `storage/runtime.json`), надсилати `Authorization: Bearer` і
додавати `?token=` лише для SSE/завантажень. Помилка API → `ApiError(status, detail)` з текстом
`detail` від сервера.
- **Перевірка:** — (прогалина; компіляція — `npm run build`)

### REQ-UI-002 — Контракт типів синхронний з backend
`frontend/src/types.ts` і `api.ts` **ПОВИННІ** відповідати моделям і ендпоінтам backend
(00, 11). Зміна API без зміни типів у тому самому PR заборонена.
- **Перевірка:** `npm run typecheck`, `npm run build` (лише TS-компіляція; JS-контрактних тестів немає — прогалина)

### REQ-UI-003 — Підтвердження high-risk джерела
На відповідь 428 від `calibrate`/`run`/`schedule` UI **ПОВИНЕН** показати повідомлення сервера, запитати
причину і повторити запит один раз з `acknowledge_high_risk=true` і `reason`; порожня причина —
скасування.
- **Перевірка:** — (прогалина)

### REQ-UI-004 — Живий журнал
UI **ПОВИНЕН** завантажити історію подій (`/events`, ≤ 500), потім підписатися на SSE і зливати
події без дублікатів за `id`; без SSE — працює polling.
- **Перевірка:** — (прогалина)

### REQ-UI-005 — Стани порожньо / завантаження / помилка
Кожна панель з даними **ПОВИННА** мати стан завантаження, порожній стан із підказкою наступного кроку
і показ помилки (toast). Без зібраного UI backend віддає сторінку-підказку (REQ-API-007).
- **Перевірка:** — (прогалина; візуальні регресійні тести відсутні — `docs/03` §7 п.14)

### REQ-UI-006 — Мова
Увесь текст інтерфейсу — **українською** (перемикача мов немає).
- **Перевірка:** рев'ю

### REQ-UI-010 — Створення задачі для OpenProcurement та JSON API
Форма створення задачі (`NewTask`) **ПОВИННА** надавати швидкі приклади для `Prozorro API` і
`Prozorro.Продажі API` (які заповнюють промпт, назву та стартовий публічний URL) і опційний
згорнутий редактор кастомного `api_source` із валідацією JSON-мапінгу до відправки; `PlanPanel`
відображає налаштування `api_source`, коли `extraction === 'api_json'`.
- **Перевірка:** `npm run typecheck`, `npm run build` (прогалина JS-рендер тестів за §4)

### REQ-UI-011 — Вкладка «Розклад і доставка» (`P1-05` + `D-01`)
`AutomationPanel` (вкладка «Розклад і доставка» в `TaskWorkspace`) **ПОВИНЕН** керувати:
- cron-розкладом (UTC-вираз, швидкі пресети інтервалів, `enabled`, `catch_up`, показ
  `next_run_at`/`last_run_at`, збереження/видалення, обробка HTTP 428 аналогічно REQ-UI-003);
- підписками доставки (`telegram` / `webhook`, фільтри `event_types`, `keywords`, `min_amount`,
  `max_amount`, `notify_on_error`, опційний HMAC-секрет без повернення відкритим текстом у списку,
  перемикач активності, кнопка «Тест» і видалення).
- **Перевірка:** `npm run typecheck`, `npm run build` (прогалина JS-рендер тестів за §4)

### REQ-UI-012 — Перегляд перевірок якості та запуск gold-set eval у UI (`P1-01`)
`TaskWorkspace` і `AutomationPanel` **ПОВИННІ** показувати статус і деталі `manifest.quality_checks`
і `manifest.eval`, а також дозволяти запуск оцінки за назвою офлайн gold-пресету та порогом
`min_f1` через `POST /api/tasks/{id}/eval`.
- **Перевірка:** `npm run typecheck`, `npm run build` (прогалина JS-рендер тестів за §4)

### REQ-UI-013 — Вкладка «Карантин» у веб-інтерфейсі (`P1-08`)
`TaskWorkspace` і `QuarantinePanel` **ПОВИННІ** показувати вкладку «Карантин» (з лічильником за
наявності елементів > 0), перелік відхилених записів із датою, джерелом, причиною і
JSON-переглядом полів, кнопки «Підтвердити в датасет» та «Відхилити», а також стани
завантаження, порожнього списку та обробку помилок.
- **Перевірка:** `npm run typecheck`, `npm run build` (прогалина JS-рендер тестів за §4)

### REQ-UI-014 — Інтерактивна черга дублікатів із merge/dismiss/unmerge у веб-інтерфейсі (`P1-02`)
`DuplicatesPanel` і `TaskWorkspace` **ПОВИННІ** бути синхронними із API-контрактом (`types.ts`, `api.ts`) і надавати:
- вибір порогу схожості та політики злиття (`confidence` | `freshness` | `completeness` | `prefer_left` | `prefer_right`);
- для кожного кандидата — порівняння полів записів A і B, показ якості ідентичності, кнопки «Злити в A», «Злити в B» і «Не дублікат»;
- перелік активних та історичних `entity_links` із кнопкою «Роз'єднати» для активних злитих записів та автоматичним оновленням лічильника рядків і таблиці даних (`onRefresh`);
- стани завантаження, порожньої черги та показ помилок (`toast`).
- **Перевірка:** `npm run typecheck`, `npm run build` (прогалина JS-рендер тестів за §4)

### REQ-UI-015 — Відображення пулу проксі, circuit breakers, JS-рендера і fallback-дзеркал у вкладці «Джерела» (`P1-06`, `P1-07`)
`SourcesPanel` у веб-інтерфейсі **ПОВИНЕН** бути синхронним із API-контрактом (`types.ts`, `api.ts`) і показувати:
- блок «Проксі та стійкість краулера» зі станом проксі (redacted host/port, health %, запити, байти, вартість USD) та списком доменних circuit breakers із кнопкою «Скинути паузу»;
- індикатори стану JS-рендера (`js_renderer`: режим, активний рушій, редагований URL сайдкара без паролів, лічильники `rendered_ok` / `fallbacks` / `errors`);
- поле редагування `fallback_urls` (API / дзеркала на випадок блокування) у формі політики домену;
- стани завантаження, порожніх налаштувань та показ помилок (`toast`).
- **Перевірка:** `npm run typecheck`, `npm run build` (прогалина JS-рендер тестів за §4)

### REQ-UI-016 — Візуальний редактор spec у `PlanPanel` та Schema Diff із відкатом у `CalibrationPanel` (`P1-10`)
Веб-інтерфейс (`PlanPanel`, `CalibrationPanel`, `TaskWorkspace`, `api.ts`, `types.ts`) **ПОВИНЕН** бути синхронним із API-контрактом і забезпечувати:
- у `PlanPanel`: додавання колонок (як стандартних/CSS/збагачення, так і AI), редагування наявної колонки (назва, тип `dtype`, PII-клас, обов'язковість, метод, ручний CSS-селектор і атрибут, промпт для AI), зміну порядку колонок (`↑`/`↓`) і видалення колонки (окрім останньої);
- у `CalibrationPanel`: відображення **Schema Diff** після калібрування (зміна стратегії, контейнера, delta score/рядків, додані/видалені/змінені поля та зміна покриття), перелік останніх версій калібрування і кнопку **«Відкотити схему»** (заблоковану під час активного запуску);
- стани завантаження, порожнього стану («Перше калібрування — попередньої версії ще немає») та показ помилок (`toast`).
- **Перевірка:** `npm run typecheck`, `npm run build` (прогалина JS-рендер тестів за §4)

### REQ-UI-017 — Налаштування розширених фільтрів та дайджесту у вкладці «Розклад і доставка»
`AutomationPanel` (`frontend/src/components/AutomationPanel.tsx`), `types.ts` і `api.ts` **ПОВИННІ** бути синхронними з API-контрактом і дозволяти:
- задавати стоп-слова, префікси CPV, регіони, фільтри полів (`ключ=значення`), режим доставки (`Миттєво` / `Щоденний дайджест`) та cron дайджесту під час створення підписки;
- бачити налаштовані фільтри, режим, час наступного/останнього дайджесту та лічильник накопичених у черзі змін для кожної підписки;
- виконувати ручне відправлення накопиченого дайджесту кнопкою «Надіслати зараз» (коли є очікуючі зміни) зі станами завантаження й toast-повідомленнями.
- **Перевірка:** `npm run typecheck`, `npm run build` (прогалина JS-рендер тестів за §4)
