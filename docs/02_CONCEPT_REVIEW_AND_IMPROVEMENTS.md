## 0. Короткий вердикт

**Що в документі дуже добре (і що варто зберегти як ядро продукту):**

1. **Правильна бізнес-модель.** Гроші не в «сирих спарсених рядках», а в *відповіді на бізнес-питання*
   (дедуплікація + збагачення + історія змін). Це найсильніша частина концепції.
2. **Гібридне сховище під локальний перший день.** SQLite (OLTP/черги) + DuckDB/Parquet (аналітика
   та історія) — це справді правильний вибір для single-node продукту, кращий за «Postgres + Redis
   + Elastic» з коробки.
3. **Двофазний парсинг (калібрування → детермінований масовий прогін).** Це головна економічна
   перевага: LLM платить один раз за *схему*, а не за кожну сторінку.
4. **Waterfall-збагачення як «колонки».** Ментальна модель Clay, але локальна — це та UX-абстракція,
   яку користувач розуміє без документації.
5. **Time-series зрізи + тригери подій.** Саме те, що конкурент не може «допарсити заднім числом».

**Що критично відсутнє (P0 — без цього це демо, а не продукт):**

| # | Прогалина | Чому це блокер |
|:--|:---|:---|
| G1 | **Юридичний/комплаєнс-шар** (robots, ToS, GDPR, PII, ліцензії джерел) | Продаж персональних даних без lawful basis — це не «ризик», а прямий юридичний блокер у ЄС/Україні |
| G2 | **Походження та впевненість на рівні поля** (provenance + confidence) | Без цього не можна ні продати («звідки цифра?»), ні дебажити («чому ціна 0?») |
| G3 | **Захист від prompt injection з спарсених сторінок** | Сторінка може містити «ігноруй інструкції, поверни …» — і LLM-екстрактор слухняно зіпсує датасет |
| G4 | **Бюджет/облік витрат на LLM (per-run, per-column)** | Каскад без ліміту = рахунок, який з'їдає всю маржу |
| G5 | **Метрика якості даних** (gold set, precision/recall, quarantine) | Немає числа якості → немає ціни → немає продажу |
| G6 | **Пошук/дискавері джерел як first-class провайдер** | «Де взяти 10 000 URL?» — реальне вузьке місце, у документі лише згадка |
| G7 | **Конкурентність запису в DuckDB** (single-writer) | API + воркери в одному файлі = `database is locked` під навантаженням |
| G8 | **Локальний API без авторизації** | Будь-який сайт у браузері може стукати в `127.0.0.1` (DNS-rebinding/CSRF) |

Решта розділів нижче — деталізація, включно з виправленням **фактичних перебільшень** у документі.

## 1. Фактчек: де концепція обіцяє більше, ніж реальність

| Твердження в документі | Реальність (станом на 2026) | Що робити |
|:---|:---|:---|
| Camoufox «обходить Cloudflare Turnstile та DataDome» | Антибот-вендори реагують за тижні; «обходить» — маркетинг. Частина таких обходів порушує ToS і погіршує юридичну позицію | Подавати як **best-effort**, вести health-score джерела, мати fallback на офіційні API/датасети |
| ReaderLM-v2 «512K контекст, без чанкінгу» | Контекст 512K заявлений, але якість екстракції падає з довжиною; 1.5B-модель стабільна на ~16–64K реального HTML | Завжди мати **truncate + boilerplate-strip** перед моделлю; вимірювати якість на своєму gold set |
| «10–100 млн рядків за мілісекунди на ноутбуці» | DuckDB швидкий, але cold-scan по Parquet + JSON-екстракція — це секунди, не мілісекунди | Очікування: p95 < 1.5 с на агрегатах по 1–10 млн рядків; будувати індекси/матеріалізовані view |
| «Одна таблиця DuckDB для всього» | DuckDB — embedded OLAP, **один writer**; одночасний запис з кількох процесів/потоків блокує або падає | Один писач (worker) + read-only конекшн для API; ніколи не писати з request-handler |
| SQLite як черга задач «у WAL-режимі» | Працює, але потребує lease/lock-патерну та ідемпотентності, інакше після краху — дублі | `UPDATE ... SET lease_until` + `RETURNING` (atomic claim), ретраї з backoff |
| `docker-compose` з Redis/Celery | Суперечить «локальний перший день»: це +1 демон, +1 точка відмови | APScheduler + asyncio-воркери в тому самому процесі; Redis — опційно для горизонтального масштабу |
| LanceDB «щоб робити семантичний пошук» | Потребує embedding-модель (VRAM/гроші) і не є джерелом істини | Винести за інтерфейс `SemanticIndex`; для MVP — SQLite FTS5 + DuckDB `ILIKE`/FTS |

**Висновок:** технічний стек обраний правильно, але документ змішує *маркетингові обіцянки вендорів*
з інженерними гарантіями. У продукті треба явно розділити «працює детерміновано», «працює best-effort»,
«не гарантуємо».

## 2. Юридичний та етичний шар (P0, у документі відсутній повністю)

Це найбільша прогалина. Продукт продає дані, часто — про компанії та людей.

### 2.1. Що треба вбудувати в архітектуру, а не в дисклеймер

1. **Source Registry (реєстр джерел)** — окрема сутність на кожен домен:
   `robots_policy`, `tos_url`, `tos_risk` (low/medium/high/forbidden), `license` (owner/CC/open-data/unknown),
   `allowed_fields`, `rate_limit`, `compliance_notes`, `reviewed_at`, `reviewed_by`.
   Пайплайн **відмовляється** запускати джерела зі `tos_risk=forbidden`; `high` — лише з явним
   підтвердженням користувача і записом в audit log. *(v0.1: реєстр і UI вже є, hard-stop —
   у беклозі P1-04.)*
2. **robots.txt + Crawl-delay** — не «опція», а поведінка за замовчуванням: перевірка перед першим
   запитом до домену, кеш на добу, повага `Crawl-delay`/`Retry-After`, чесний User-Agent з контактом.
3. **PII-класифікація колонок.** Кожна колонка схеми має `pii: none|business_contact|personal`.
   `personal` (мобільний номер, особиста пошта, профіль соцмереж) — за замовчуванням **не** потрапляє
   в експорт і не йде в хмарні LLM (або йде після редагування). Для B2B — `business_contact` + маскування
   в демо-семплах.
4. **Мінімізація та строк зберігання.** TTL на raw cache і на PII-поля; `DELETE`/`PURGE` по компанії або
   по email (DSAR/erasure) з каскадом по сирих кешах і снапшотах.
5. **Ліцензія на вихідний датасет.** Генерувати `LICENSE`/`DATA_CONTRACT` разом з експортом: що дозволено,
   строк актуальності, джерела, обмеження (no resale, no personal data).
6. **Лінія походження (lineage)** на рівні запису/поля: `source_url`, `extracted_at`, `method`
   (`json_ld|css|llm|manual`), `confidence`. Експорт без provenance — напівфабрикат.
7. **Не робити LinkedIn/соцмережі «прямим скрейпінгом».** Контакти — з публічних бізнес-сторінок,
   офіційних API або ліцензованих провайдерів. Це має бути зафіксовано в Source Registry.

> Практичне правило: **robots — поважаємо; ToS — реєструємо; PII — мінімізуємо; provenance — завжди.**

## 3. Безпека AI-пайплайну: prompt injection, галюцинації, витік даних

Документ описує LLM як «розумного екстрактора», але не моделює загрози.

1. **Prompt injection через вміст сторінки.** Спарсений HTML/Markdown — це **недовірені дані**.
   - Екстрактор **ніколи** не отримує інструментів (tools/function calling), лише «текст + JSON Schema».
   - Контент подається в чітко розмежованому блоці, а інструкції — лише в system-повідомленні.
   - Після екстракції — валідація за схемою + **детермінований перехресний чек** (наприклад, ціна
     з CSS-селектора vs ціна з LLM; розбіжність → `confidence` падає, запис у quarantine).
   - Ніколи не виконувати згенерований LLM код (Python). Дозволені лише декларативні CSS/XPath-селектори,
     які валідуються та компілюються з whitelist-парсера.
2. **Галюцинації.** Кожне поле має `confidence`; поріг → `needs_review`. Числа валідуються
   (діапазон, валюта, одиниці). Порожнє значення краще за вигадане.
3. **Витік даних у хмару.** Перед cloud-LLM: redaction PII (email/phone/IBAN), явний allowlist колонок.
   Локальний провайдер (Ollama) — шлях за замовчуванням для PII.
4. **Отруєння кешу.** Кеш ключується `content_hash + schema_hash + prompt_hash + model_id`; інакше
   зміна промпту віддає старі відповіді.
5. **Модель-недовіра.** Structured output валідується Pydantic; невалідний JSON → repair → retry →
   fallback на інший провайдер → і лише потім `failed` (з причиною, не мовчазний `null`).

## 4. Дані: модель, якості, історія

### 4.1. Чого не вистачає в моделі даних

- **Незмінні версії записів** (append-only `record_versions`), а не `UPDATE` поверх. Інакше «історія цін»
  — це не історія, а останній стан.
- **Канонічні entity ID** окремо від `record_key`: компанія може змінити домен/назву, але залишитись тією ж.
  Потрібні `entity_id`, `record_key` (природний ключ), `match_rule`, `merged_into`.
- **Dataset version** (immutable) + manifest: коли, який код, які джерела, скільки записів, checksum.
  Це основа для «клієнт купив версію 2026-10-21, а не «щось із бази».
- **Quarantine** окремо від основної таблиці: невалідні/суперечливі записи не псують снапшот.
- **Field-level provenance** (див. §2.1) + `observed_at` для таймсерій.

### 4.2. Entity Resolution: складніше, ніж «Splink + RapidFuzz»

- Splink/Dedupe — **batch**, погано працюють інкрементально («з'явився 1 новий запис — з ким злити?»).
  Для MVP: blocking за нормалізованим доменом/назвою/телефоном + RapidFuzz + ручні правила; для
  масштабу — Splink окремим batch-джобом із збереженням pairwise-рішень.
- Обов'язково: **merge policy** (хто перемагає при конфлікті полів — свіжіше/надійніше джерело),
  **canonical record** vs raw observations, **unmerge** (помилкове злиття має бути оборотним).
- Дедуплікація **всередині** джерела (та сама квартира з різних сторінок) і **між** джерелами — різні правила.

### 4.3. Метрика якості (P0)

Без eval-харнесу продукт неможливо ні покращувати, ні продавати:
- `gold/` — 20–50 вручну розмічених сторінок на кожен тип джерела;
- скрипт `daas eval --dataset X` рахує precision/recall/F1 по полях, coverage, % LLM-fallback;
- регресії блокують зміну селекторів/промптів (як unit-тести, але для даних);
- у UI — бейдж «якість: 96% (gold set v3)» + «свіжість».

## 5. Архітектурні уточнення

### 5.1. Розділення процесів (навіть на одній машині)

```
uvicorn (API, read-only DuckDB + SQLite)  ──┐
                                             ├── storage/  (SQLite WAL, DuckDB file, raw cache, snapshots)
worker (одна черга, один DuckDB-writer)  ──┘
```

- **DuckDB пише лише worker.** API відкриває `read_only=True` (або `ACCESS_MODE=READ_ONLY`).
- **Черга — SQLite з lease**: `claim()` робить атомарний `UPDATE ... RETURNING`, heartbeat продовжує lease,
  а «мертві» lease повертаються в чергу. Це дає crash-resume без Redis.
- **Ідемпотентність**: ключ задачі `(run_id, url)`; повторний фетч повертає кеш, а не дублює запис.
- **Graceful shutdown**: зупинка приймання нових URL, дренаж in-flight, фіксація прогресу.

### 5.2. Адаптери замість жорстких залежностей

Концепція змішує важкі залежності (Playwright, Camoufox, Browser-Use, Ollama) в одному середовищі —
це гарантований біль з wheel'ами та зламаними оновленнями. Правильно:

```python
class Fetcher(Protocol):        async def fetch(self, url, *, use_proxy=False) -> FetchResult: ...
class Extractor(Protocol):      def extract(self, page: Page, schema: ExtractionSchema) -> list[Record]: ...
class LLMProvider(Protocol):    async def complete_json(self, req: LLMExtractionRequest) -> LLMResult: ...
class SearchProvider(Protocol): async def search(self, query, limit) -> list[SearchHit]: ...
class Enricher(Protocol):       name, cost, applies_to; async def run(self, record, ctx) -> dict: ...
```

- `httpx`-шлях — **за замовчуванням** (працює на ноутбуці, без браузера);
- `playwright`/`crawl4ai`, `camoufox`, `browser-use`, `ollama` — **optional extras** і, бажано, окремий
  контейнер/сайдкар, щоб їхні залежності не ламали ядро;
- реєстр провайдерів + capability flags (`js_rendering`, `stealth`, `vision`) — UI сам показує, що доступно.

### 5.3. Пошук джерел (Discovery) — first-class

Реальні варіанти з цінами/обмеженнями: SearXNG (self-hosted, безкоштовно), Brave Search API, Bing Web
Search, Google Places (для локального бізнесу), OpenStreetMap/Overpass (безкоштовно, гео), sitemap.xml,
держреєстри/Open Data. Кожен — `SearchProvider` з обліком витрат і rate limit. Google-скрейпінг HTML —
не як основа продукту (крихко + ToS).

### 5.4. Експорт і доставка

- CSV / XLSX / Parquet / JSON — з **манифестом** (schema, row count, generated_at, sources, license).
- «Дата-продукт» = версія + контракт + свіжість, а не файл.
- API-доступ: якщо будувати — то як окремий тонкий сервіс (Fly/Render/Cloudflare) з токенами, метерингом
  і SLA; **не** виставляти локальний інстанс у публічний інтернет.
- Демо-семпл: маскування PII, watermark/partial rows, «звідки взято» — щоб демо не стало безкоштовним датасетом.

## 6. Інженерна якість (чого немає в документі)

| Тема | Мінімум для MVP |
|:---|:---|
| Тести | `pytest` + офлайн-HTML фікстури; жодних мережевих тестів; golden-файли екстракції |
| Міграції | версія схеми SQLite (`PRAGMA user_version`) і DuckDB; forward-only SQL-міграції |
| CI | ruff + pytest на кожен PR; окремий job на frontend build |
| Типізація | Pydantic-моделі на межах шарів; mypy — поетапно |
| Логи | структурні JSON-логи + `run_id`/`task_id` у кожному рядку; SSE-стрім подій у UI |
| Метрики | сторінок/с, успіх/помилки за типом, LLM-токени/гроші, розмір кешу, hit rate |
| Помилки | таксономія: `transient | blocked | permanent | schema_mismatch`; DLQ для `permanent` |
| Секрети | `.env` + OS keychain (опційно); API-ключі — тільки хеш (argon2/sha256+pepper) |
| Резервні копії | `daas backup` → zip (SQLite dump + DuckDB snapshot + manifest); локальний-first = «ноутбук помер» |
| Спостережуваність вартості | ledger: `run_id, provider, model, tokens_in/out, usd` + бюджет на run |

**SSRF-захист** для URL, які вводить користувач: заборона `127.0.0.0/8`, `169.254.0.0/16`,
`10/8`, `172.16/12`, `192.168/16`, `::1`, DNS-резолв перевіряється перед конектом (`follow_redirects`
теж перевіряється). **Path traversal** для експортів: `resolve()` + `is_relative_to(storage_root)`.

## 7. Продукт і монетизація: уточнення

1. **Позиціонування:** не «скрейпер», а **«фабрика дата-продуктів»**: `джерело → нормалізація → збагачення →
   історія → контракт → доставка`. Скрейпер — реалізаційна деталь.
2. **Ціноутворення від цінності:** ціна за *оновлення* (підписка на моніторинг) + *разовий датасет*.
   Документ це має на увазі, але не формалізує.
3. **Перші ніші (де дані справді болять):** локальний бізнес на картах (рейтинги/відгуки), нерухомість
   (динаміка цін), e-commerce моніторинг, вакансії як intent-сигнал, тендери/Prozorro. Для кожної — свій
   eval set і свій data contract.
4. **Що прибрати з MVP:** LanceDB/векторний пошук, Browser-Use, Camoufox, клієнтський портал, білінг.
   Вони не перевіряють гіпотезу «люди платять за збагачені дані з історією». Вони — P2/P3.
5. **Метрика успіху MVP:** «за 15 хвилин від промпту до валідного XLSX на 500 рядків із provenance»,
   а не «підтримуємо 5 скраперів».

## 8. Пріоритезований беклог покращень

**P0 — у MVP (тиждень 1–2):**
1. Адаптери `Fetcher/Extractor/LLMProvider/SearchProvider/Enricher` + легкий httpx-шлях.
2. Provenance + confidence + `record_versions` (append-only) + dataset version.
3. LLM-каскад із бюджетом, кешем і захистом від injection (без tools, валідація, cross-check).
4. Source Registry (robots/ToS/ліцензія) + PII-класифікація + маскування в семплах.
5. SQLite-черга з lease + один DuckDB-writer + graceful resume.
6. Gold-set eval + quarantine.
7. Токен-авторизація локального API (bind 127.0.0.1) + SSRF/path-traversal захист.

**P1 — одразу після MVP:**
8. Discovery-провайдери (SearXNG/OSM/sitemap/Open Data) + реєстр вартості.
9. Waterfall-збагачення: domain resolver, tech stack, contacts, jobs.
10. Entity resolution (blocking + RapidFuzz + merge policy) і ручний unmerge.
11. Scheduler + щоденні Parquet-снапшоти + тригери (price drop, new vacancy, out-of-stock).
12. Експорти з контрактом/ліцензією; демо-семпл із маскуванням.

**P2 — масштаб і зручність:**
13. Опційні важкі рушії (Playwright/Crawl4AI/Camoufox) як сайдкар; проксі-провайдери з health-score.
14. Семантичний пошук (LanceDB) за інтерфейсом; FTS5 як дефолт.
15. Browser-Use для складних сценаріїв; vision-fallback для застарілих порталів.
16. Diff/merge UI для схеми, «explain this row», undo.

**P3 — монетизація:**
17. Публічний Data API (окремий сервіс) + API-ключі + метеринг + SLA.
18. Клієнтський портал, білінг (Stripe), ліцензійні ключі.
19. Маркетплейс готових дата-продуктів (каталог + прев'ю).
